1.1 Introduction : Pourquoi l'authentification est critique

L'authentification répond à la question fondamentale : "Qui êtes-vous ?"

Sans authentification sur l'API SmartCity :

  • N'importe qui pourrait supprimer tous les événements
  • Création massive de spam
  • Accès aux données personnelles de tous les citoyens
  • Impossibilité de tracer les actions

Les méthodes d'authentification en bref

Avant de plonger dans les détails, voici un aperçu rapide des principales méthodes :

🔐 Basic Authentication

La méthode la plus simple. Le client envoie username et password encodés en Base64 dans chaque requête. Simple mais peu sécurisé (credentials visibles si interceptés). Utilisé pour les APIs internes ou le prototypage.

🍪 Session Cookies

Après connexion, le serveur crée une session unique stockée en mémoire ou en base de données. Le client reçoit un cookie contenant l'ID de session. Le serveur vérifie la session à chaque requête. Classique pour les applications web traditionnelles.

🎫 JWT (JSON Web Tokens)

Un token auto-contenu qui inclut toutes les informations nécessaires (utilisateur, permissions, expiration). Pas besoin de stockage serveur, donc "stateless". Le token est signé cryptographiquement pour garantir son intégrité. Standard moderne pour les APIs REST et les applications mobiles.

🔑 OAuth 2.0

Un protocole de délégation d'autorisation (pas d'authentification directe). Permet à une application tierce d'accéder aux ressources d'un utilisateur sans avoir son mot de passe. L'utilisateur autorise l'application via un serveur d'autorisation qui délivre des tokens. Standard pour les APIs publiques (Google, Facebook, GitHub...).

🔐 API Keys

Des clés aléatoires longues et uniques générées par le serveur pour chaque client. Plus sécurisées que Basic Auth car révocables instantanément. Utilisées principalement pour les APIs B2B (Business-to-Business) et les services backend internes. Chaque clé peut avoir des permissions spécifiques (scopes).

Évolution historique

L'évolution des méthodes d'authentification suit les besoins de l'architecture web :

  • 1990s : Basic Authentication devient le standard HTTP
  • 2000s : Session cookies avec stockage serveur (pour les applications web traditionnelles)
  • 2010s : JWT émerge pour les APIs stateless (RFC 7519 en 2015) - répond au besoin de scalabilité
  • 2012+ : OAuth 2.0 s'impose pour les APIs publiques (délégation d'autorisation)

Parts de marché 2024 (Stack Overflow Survey)

Répartition d'utilisation des différentes méthodes dans l'industrie :

  • JWT : 71% des APIs REST modernes (standard pour les applications mobiles et SPAs)
  • Session cookies : 42% (applications web traditionnelles avec serveur de rendu)
  • OAuth 2.0 : 28% (APIs publiques avec délégation - Google, Facebook, GitHub...)
  • API Keys : 25% (APIs internes, services backend, intégrations B2B comme Stripe, Twilio, SendGrid, AWS)
💡 Note importante

Les API Keys ne font pas partie de l'évolution historique car elles sont plutôt une méthode pratique qui coexiste avec les autres. Elles sont particulièrement adaptées aux intégrations entre services (B2B) où chaque client reçoit une clé unique avec des permissions spécifiques.

1.2 Basic Authentication : La simplicité avant tout

Principe de fonctionnement

Basic Authentication est la méthode la plus simple définie dans le standard HTTP. Le client envoie le username et password encodés en Base64 dans le header Authorization à chaque requête.

Format de la requête :
GET /api/events HTTP/1.1
Host: api.smartcity.local
Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=
⚠️ Point critique

Base64 n'est PAS du chiffrement, c'est juste un encodage. N'importe qui peut décoder instantanément :

echo "dXNlcm5hbWU6cGFzc3dvcmQ=" | base64 -d
# Résultat : username:password

Implémentation

Voici comment implémenter Basic Auth en Node.js/Express. Le middleware extrait les credentials du header, les décode, et vérifie leur validité :

const express = require('express');
const app = express();

function basicAuth(req, res, next) {
  const authHeader = req.headers.authorization;
  
  if (!authHeader || !authHeader.startsWith('Basic ')) {
    res.setHeader('WWW-Authenticate', 'Basic realm="SmartCity API"');
    return res.status(401).json({ 
      error: 'Authentication required',
      message: 'Please provide username and password'
    });
  }
  
  const base64Credentials = authHeader.split(' ')[1];
  const credentials = Buffer.from(base64Credentials, 'base64').toString('utf-8');
  const [username, password] = credentials.split(':');
  
  // En production : vérifier dans la DB avec bcrypt
  if (username === 'admin' && password === 'secret123') {
    req.user = { username, role: 'admin' };
    return next();
  }
  
  res.status(401).json({ error: 'Invalid credentials' });
}

app.get('/api/events', basicAuth, (req, res) => {
  res.json({ 
    message: `Hello ${req.user.username}`,
    events: [] 
  });
});

Avantages et inconvénients

✅ Avantages :
  • Extrêmement simple à implémenter
  • Supporté nativement par tous les navigateurs et outils HTTP
  • Pas besoin de gérer des sessions ou tokens côté serveur
❌ Inconvénients majeurs :
  • Credentials envoyés à chaque requête (risques d'interception)
  • Impossible à révoquer sans changer le password
  • Pas de mécanisme de logout
  • HTTPS absolument obligatoire
💡 Quand l'utiliser

APIs internes derrière VPN, scripts automatisés, prototypage

1.3 API Keys : L'amélioration pratique

Principe de fonctionnement

Au lieu que le client renvoie username/password à chaque requête, le serveur délivre une clé aléatoire unique lors de la première authentification. Cette clé sert ensuite d'identifiant pour toutes les requêtes futures.

Format de la requête :
GET /api/events HTTP/1.1
X-API-Key: api_votre_cle_ici

Implémentation

Le système nécessite la génération de clés sécurisées et leur validation. Les clés sont stockées en base avec les permissions associées.

1. Génération de la clé API
const crypto = require('crypto');

// Génération d'une API key cryptographiquement sécurisée
// crypto.randomBytes(32) génère 32 bytes aléatoires (256 bits)
// .toString('hex') les convertit en chaîne hexadécimale (64 caractères)
function generateApiKey() {
  return 'sk_live_' + crypto.randomBytes(32).toString('hex');
  // Résultat : préfixe "sk_live_" suivi de 64 caractères hexadécimaux aléatoires
}
2. Stockage des clés (en production : base de données)
// Structure de stockage : Map pour la démo, en production utiliser PostgreSQL/MySQL
// Chaque clé est associée à :
// - userId : l'utilisateur propriétaire
// - name : un nom descriptif (ex: "Mobile App", "Dashboard Admin")
// - scopes : les permissions accordées (read:events, write:events, etc.)
const apiKeys = new Map([
  ['sk_live_abc123', { 
    userId: 1, 
    name: 'Mobile App',
    scopes: ['read:events', 'write:events']  // Permissions granulaires
  }]
]);
3. Middleware de validation
// Middleware Express qui vérifie la présence et la validité de la clé API
function validateApiKey(req, res, next) {
  // 1. Extraire la clé du header X-API-Key
  const apiKey = req.headers['x-api-key'];
  
  // 2. Vérifier que la clé est présente
  if (!apiKey) {
    return res.status(401).json({
      error: 'API key required',
      message: 'Include X-API-Key header in your request'
    });
  }
  
  // 3. Rechercher la clé dans notre stockage (en prod : requête DB)
  const keyData = apiKeys.get(apiKey);
  
  // 4. Vérifier que la clé existe et est valide
  if (!keyData) {
    return res.status(401).json({ error: 'Invalid API key' });
  }
  
  // 5. Logger l'utilisation (pour analytics et rate limiting)
  // ⚠️ IMPORTANT : Ne jamais logger la clé complète, seulement un préfixe
  console.log(`API key ${apiKey.substring(0, 15)}... used by ${keyData.name}`);
  
  // 6. Ajouter les informations de l'utilisateur au contexte de la requête
  req.user = keyData;
  
  // 7. Passer au middleware suivant ou à la route
  next();
}
4. Utilisation dans les routes
// Appliquer le middleware sur une route spécifique
app.get('/api/events', validateApiKey, (req, res) => {
  // À ce stade, req.user contient les infos de la clé API
  // On peut vérifier les scopes si nécessaire
  res.json({ 
    message: `Hello ${req.user.name}`,
    scopes: req.user.scopes  // Afficher les permissions de la clé
  });
});

Bonnes pratiques essentielles

1. Préfixez vos clés (comme Stripe)
  • sk_live_ : Secret Key production
  • sk_test_ : Secret Key développement
  • pk_live_ : Public Key (si applicable)
2. Ne loggez JAMAIS les clés complètes
❌ Dangereux
// ❌ DANGEREUX : La clé complète apparaît dans les logs
console.log(`API key: ${apiKey}`);
// Si les logs sont compromis, l'attaquant a la clé complète
✅ Sécurisé
// ✅ SÉCURISÉ : Seulement les premiers caractères
console.log(`API key: ${apiKey.substring(0, 15)}...`);
// Exemple : "API key: sk_live_xxxxx..."
3. Permissions granulaires

Chaque clé doit avoir des scopes spécifiques pour limiter les actions possibles :

// Exemple de scopes granulaires
const scopes = {
  'read:events': 'Lire les événements',
  'write:events': 'Créer/modifier des événements',
  'delete:events': 'Supprimer des événements',
  'admin:users': 'Gérer les utilisateurs (admin uniquement)'
};

// Vérifier les scopes dans le middleware
function checkScope(requiredScope) {
  return (req, res, next) => {
    if (!req.user.scopes.includes(requiredScope)) {
      return res.status(403).json({ 
        error: 'Forbidden',
        message: `Scope '${requiredScope}' required`
      });
    }
    next();
  };
}

// Utilisation
app.delete('/api/events/:id', validateApiKey, checkScope('delete:events'), (req, res) => {
  // Seulement les clés avec le scope 'delete:events' peuvent accéder
});
4. Rotation régulière

Nouvelle clé tous les 90 jours pour limiter les risques en cas de fuite.

Avantages et inconvénients

✅ Avantages :
  • Simple et compréhensible
  • Révocable instantanément : supprimer la clé en DB = accès coupé immédiatement
  • Traçable : savoir quelle app fait quelle requête grâce au nom de la clé
  • Un utilisateur peut avoir plusieurs clés (une pour mobile, une pour web, etc.)
❌ Inconvénients :
  • Stateful : requête DB pour validation à chaque requête (impact performance)
  • Pas d'expiration automatique (doit être géré manuellement)
  • Risque de fuite si la clé est exposée (logs, code source, etc.)
🌐 Utilisé par

Stripe, SendGrid, Twilio, AWS, et de nombreuses autres APIs B2B

1.4 JWT (JSON Web Tokens) : L'authentification stateless

Le problème que JWT résout

Avec Basic Auth ou API Keys, le serveur doit interroger la base de données à chaque requête. Avec les sessions, le serveur maintient un état en mémoire.

JWT permet une authentification stateless : toutes les informations sont dans le token lui-même. Pas de requête DB pour valider.

Structure d'un JWT

Un JWT est composé de 3 parties séparées par des points :

eyJhbGc...header.eyJzdWI...payload.SflKxw...signature
1️⃣ Header - Métadonnées

Contient l'algorithme de signature et le type de token :

{
  "alg": "HS256",  // Algorithme de signature (HMAC SHA256)
  "typ": "JWT"     // Type de token
}
2️⃣ Payload - Données utilisateur

Contient les informations sur l'utilisateur et les métadonnées du token :

{
  "sub": "123",                    // Subject (ID utilisateur)
  "email": "marie@example.com",    // Email de l'utilisateur
  "role": "admin",                 // Rôle/permissions
  "iat": 1516239022,               // Issued At (timestamp de création)
  "exp": 1516242622                // Expiration (timestamp)
}
3️⃣ Signature - Garantit l'intégrité

La signature est calculée ainsi :

HMACSHA256(
  base64(header) + "." + base64(payload),
  secret_key
)
🔒 Sécurité de la signature

La signature prouve que le token n'a pas été modifié. Si quelqu'un change le payload, la validation échouera car la signature ne correspondra plus.

Création et validation

Exemple complet avec login et middleware de validation :

1. Installation des dépendances
npm install jsonwebtoken bcrypt
2. Route de login (génération du token)
const jwt = require('jsonwebtoken');
const bcrypt = require('bcrypt');

// Secret JWT (en production : variable d'environnement, minimum 256 bits)
const SECRET = process.env.JWT_SECRET;

// Route POST /api/auth/login
app.post('/api/auth/login', async (req, res) => {
  // 1. Récupérer email et password depuis le body
  const { email, password } = req.body;
  
  // 2. Chercher l'utilisateur dans la base de données
  const user = await prisma.user.findUnique({ where: { email } });
  
  // 3. Vérifier que l'utilisateur existe et que le password est correct
  if (!user || !(await bcrypt.compare(password, user.password_hash))) {
    return res.status(401).json({ error: 'Invalid credentials' });
  }
  
  // 4. Générer le JWT avec jwt.sign()
  // Paramètres :
  // - payload : données à inclure dans le token
  // - SECRET : clé secrète pour signer le token
  // - options : expiration, issuer, audience
  const token = jwt.sign(
    {
      sub: user.id,        // Subject : ID de l'utilisateur
      email: user.email,   // Email pour affichage
      role: user.role      // Rôle pour les permissions
    },
    SECRET,
    {
      expiresIn: '24h',                    // Token valide 24 heures
      issuer: 'smartcity-api',              // Qui a créé le token
      audience: 'smartcity-clients'         // Pour qui est le token
    }
  );
  
  // 5. Renvoyer le token au client
  res.json({
    access_token: token,      // Le token JWT
    token_type: 'Bearer',     // Type d'authentification
    expires_in: 86400         // Durée en secondes (24h = 86400s)
  });
});
3. Middleware de validation
// Middleware Express pour valider le JWT à chaque requête
function authenticateJWT(req, res, next) {
  // 1. Extraire le header Authorization
  const authHeader = req.headers.authorization;
  
  // 2. Vérifier que le header existe et commence par "Bearer "
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({
      error: 'No token provided',
      message: 'Include Authorization: Bearer  header'
    });
  }
  
  // 3. Extraire le token (enlever "Bearer " du début)
  const token = authHeader.split(' ')[1];
  
  // 4. Vérifier et décoder le token
  try {
    // jwt.verify() :
    // - Vérifie la signature
    // - Vérifie l'expiration (exp)
    // - Vérifie l'issuer (iss) et l'audience (aud)
    // - Retourne le payload décodé si tout est valide
    const decoded = jwt.verify(token, SECRET, {
      issuer: 'smartcity-api',        // Vérifier que le token vient de notre API
      audience: 'smartcity-clients',   // Vérifier que le token est pour nos clients
      algorithms: ['HS256']            // Liste blanche : seulement HS256 accepté
    });
    
    // 5. Ajouter les données utilisateur au contexte de la requête
    req.user = decoded;
    
    // 6. Passer au middleware suivant ou à la route
    next();
  } catch (err) {
    // Gestion des erreurs spécifiques
    if (err.name === 'TokenExpiredError') {
      return res.status(401).json({
        error: 'Token expired',
        message: 'Please login again'
      });
    }
    // Autres erreurs : signature invalide, token malformé, etc.
    return res.status(401).json({ error: 'Invalid token' });
  }
}
4. Utilisation dans les routes
// Appliquer le middleware sur une route protégée
app.get('/api/events', authenticateJWT, (req, res) => {
  // À ce stade, req.user contient les données du token décodé
  // On peut accéder à req.user.email, req.user.role, etc.
  res.json({
    message: `Hello ${req.user.email}`,
    role: req.user.role,
    // ... données de l'API
  });
});

Algorithmes de signature

Algorithmes symétriques (même secret pour signer/vérifier)
  • HS256 : Le plus courant, simple et rapide (HMAC SHA-256)
  • HS384, HS512 : Hash plus long, plus sécurisé mais plus lent
✅ Utiliser HS256 si :

Monolithe ou serveurs partageant le même secret. Simple et efficace pour la plupart des cas.

Algorithmes asymétriques (clé privée/publique)
  • RS256 : Clé privée pour signer, clé publique pour vérifier (RSA)
  • ES256 : Plus performant que RSA, basé sur ECDSA
✅ Utiliser RS256 si :

Architecture microservices où un seul service crée les tokens et plusieurs services les vérifient. Le service auth garde la clé privée, les autres services utilisent la clé publique.

Exemple RS256 : Architecture microservices

Utile quand un service d'authentification crée les tokens et plusieurs services les vérifient :

const fs = require('fs');

// Générer les clés (une seule fois) :
// openssl genrsa -out private.key 2048
// openssl rsa -in private.key -pubout -out public.key

// Lire les clés depuis les fichiers
const privateKey = fs.readFileSync('private.key');
const publicKey = fs.readFileSync('public.key');

// ===== SERVICE AUTH (création des tokens) =====
// Ce service garde la clé privée et signe les tokens
const token = jwt.sign(
  { sub: user.id, email: user.email },
  privateKey,                    // Clé privée pour signer
  { algorithm: 'RS256', expiresIn: '1h' }
);

// ===== SERVICE EVENTS (vérification des tokens) =====
// Ce service reçoit seulement la clé publique et vérifie les tokens
const decoded = jwt.verify(token, publicKey, { 
  algorithms: ['RS256']  // Liste blanche : seulement RS256
});

// Avantage : si la clé publique est compromise, l'attaquant ne peut pas créer de tokens
// Seule la clé privée (gardée secrète) permet de signer

Avantages et inconvénients

✅ Avantages :
  • Stateless : Pas de requête DB pour valider (performance)
  • Scalable : Fonctionne en load balancing sans session partagée
  • Cross-domain : Utilisable sur plusieurs domaines
  • Mobile-friendly : Juste un header, pas de cookies
  • Auto-contenu : Toutes les infos dans le token
❌ Inconvénients :
  • Impossible à révoquer instantanément (sauf avec refresh tokens + blacklist)
  • Plus gros qu'un ID de session (300-500 bytes vs 20 bytes)
  • Pas de gestion d'état : Si le rôle change, les tokens existants gardent l'ancien
  • Payload visible : Encodé en Base64, pas chiffré (ne pas mettre de données sensibles)
1.5 Refresh Tokens : Gérer l'expiration intelligemment

Le problème

Dilemme de sécurité :

  • Token court (15min) = utilisateur doit se reconnecter souvent (mauvaise UX)
  • Token long (24h) = si volé, l'attaquant a 24h d'accès (risque élevé)

La solution : Deux tokens

Access Token
  • Courte durée de vie (15min - 1h)
  • Utilisé pour toutes les requêtes API
  • Stocké en mémoire ou cookie httpOnly
Refresh Token
  • Longue durée de vie (7-30 jours)
  • Utilisé UNIQUEMENT pour obtenir un nouveau access token
  • Stocké en base de données (révocable)

Flow complet

  1. Login → Access Token (15min) + Refresh Token (7j)
  2. Utiliser Access Token pour API calls
  3. Access Token expire → Appeler /auth/refresh avec Refresh Token
  4. Recevoir nouveau Access Token (15min)
  5. Répéter jusqu'à expiration du Refresh Token
  6. Redemander login complet

Implémentation

1. Configuration des secrets
// Deux secrets différents pour plus de sécurité
// Si l'access token est compromis, le refresh token reste valide
const ACCESS_TOKEN_SECRET = process.env.ACCESS_TOKEN_SECRET;
const REFRESH_TOKEN_SECRET;
2. Route de login (création des deux tokens)
// Route POST /api/auth/login
app.post('/api/auth/login', async (req, res) => {
  // 1. Valider les credentials (email + password)
  const user = await validateCredentials(req.body);
  
  // 2. Générer l'Access Token (court : 15 minutes)
  // Contient les infos nécessaires pour les requêtes API
  const accessToken = jwt.sign(
    { 
      sub: user.id,        // ID utilisateur
      email: user.email,   // Email pour affichage
      role: user.role      // Rôle pour les permissions
    },
    ACCESS_TOKEN_SECRET,
    { expiresIn: '15m' }   // Expire dans 15 minutes
  );
  
  // 3. Générer le Refresh Token (long : 7 jours)
  // Contient seulement l'ID utilisateur (minimal)
  const refreshToken = jwt.sign(
    { sub: user.id },       // Seulement l'ID, pas d'autres infos
    REFRESH_TOKEN_SECRET,
    { expiresIn: '7d' }     // Expire dans 7 jours
  );
  
  // 4. Stocker le refresh token en DB pour pouvoir le révoquer
  // Structure de table : id, token, userId, expiresAt, revoked
  await prisma.refreshToken.create({
    data: {
      token: refreshToken,  // Le token complet
      userId: user.id,      // Lien vers l'utilisateur
      expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000), // 7 jours
      revoked: false        // Par défaut, non révoqué
    }
  });
  
  // 5. Renvoyer les deux tokens au client
  res.json({
    access_token: accessToken,   // Pour les requêtes API
    refresh_token: refreshToken,  // Pour obtenir un nouveau access token
    token_type: 'Bearer',
    expires_in: 900              // 15 minutes en secondes
  });
});
3. Route de refresh (obtenir un nouveau access token)
// Route POST /api/auth/refresh
app.post('/api/auth/refresh', async (req, res) => {
  // 1. Récupérer le refresh token depuis le body
  const { refresh_token } = req.body;
  
  // 2. Vérifier que le refresh token est présent
  if (!refresh_token) {
    return res.status(401).json({ error: 'Refresh token required' });
  }
  
  try {
    // 3. Vérifier la signature du refresh token
    // Si la signature est invalide, jwt.verify() lèvera une exception
    const decoded = jwt.verify(refresh_token, REFRESH_TOKEN_SECRET);
    
    // 4. Vérifier que le refresh token existe en DB et n'est pas révoqué
    // C'est ici qu'on peut révoquer un token même s'il n'est pas expiré
    const storedToken = await prisma.refreshToken.findFirst({
      where: {
        token: refresh_token,              // Le token correspond
        userId: decoded.sub,                // Pour le bon utilisateur
        revoked: false,                     // Non révoqué
        expiresAt: { gt: new Date() }       // Pas expiré
      }
    });
    
    // 5. Si le token n'existe pas ou est révoqué/expiré
    if (!storedToken) {
      return res.status(401).json({ 
        error: 'Invalid or expired refresh token' 
      });
    }
    
    // 6. Récupérer les infos utilisateur à jour (au cas où le rôle aurait changé)
    const user = await prisma.user.findUnique({ 
      where: { id: decoded.sub } 
    });
    
    // 7. Générer un NOUVEAU access token (15 minutes)
    const newAccessToken = jwt.sign(
      { 
        sub: user.id, 
        email: user.email, 
        role: user.role  // Rôle à jour
      },
      ACCESS_TOKEN_SECRET,
      { expiresIn: '15m' }
    );
    
    // 8. Renvoyer le nouveau access token (pas de nouveau refresh token)
    res.json({
      access_token: newAccessToken,  // Nouveau token
      token_type: 'Bearer',
      expires_in: 900                // Toujours 15 minutes
    });
  } catch (err) {
    // Erreur : signature invalide, token expiré, etc.
    return res.status(401).json({ error: 'Invalid refresh token' });
  }
});
4. Route de logout (révocation du refresh token)
// Route POST /api/auth/logout
// Nécessite un access token valide (middleware authenticateJWT)
app.post('/api/auth/logout', authenticateJWT, async (req, res) => {
  // 1. Récupérer le refresh token depuis le body
  const { refresh_token } = req.body;
  
  // 2. Révoquer le refresh token en DB
  // On le marque comme révoqué plutôt que de le supprimer
  // Avantage : on peut tracer les tentatives d'utilisation après révocation
  await prisma.refreshToken.updateMany({
    where: { 
      token: refresh_token,        // Le token à révoquer
      userId: req.user.sub         // Vérifier que c'est bien l'utilisateur connecté
    },
    data: { revoked: true }        // Marquer comme révoqué
  });
  
  // 3. Note : L'access token reste valide jusqu'à expiration (15min)
  // Mais le refresh token est révoqué, donc pas de nouveau access token possible
  res.json({ message: 'Logged out successfully' });
});

Avantages de ce pattern

✅ Sécurité

Access token court (15min) limite les dégâts si volé. Même si un attaquant intercepte l'access token, il n'a que 15 minutes d'accès maximum.

✅ UX

Pas de reconnexion fréquente. L'utilisateur reste connecté pendant 7 jours grâce au refresh token, mais avec des access tokens courts pour la sécurité.

✅ Révocation

Les refresh tokens sont stockés en DB et révocables instantanément. Si un utilisateur se déconnecte ou qu'on détecte une compromission, on peut révoquer immédiatement.

💡 Bonne pratique

En production, stockez le refresh token dans un cookie httpOnly et secure pour éviter les attaques XSS. L'access token peut rester en mémoire JavaScript pour les requêtes API.

1.6 Sécurité JWT : Les 5 règles d'or

Pour sécuriser correctement vos JWT, suivez ces 5 règles essentielles :

Règle 1 : Jamais de données sensibles dans le payload

Le payload JWT est juste encodé en Base64, pas chiffré. N'importe qui peut le décoder sur jwt.io.

❌ DANGEREUX
// ❌ DANGEREUX : Données sensibles dans le payload
const token = jwt.sign({
  sub: user.id,
  password: user.password,      // VISIBLE PAR TOUS ! N'importe qui peut décoder
  credit_card: user.card,        // VISIBLE PAR TOUS ! Fuite de données
  secret_key: user.apiKey        // VISIBLE PAR TOUS ! Compromission totale
}, SECRET);

// Le payload est encodé en Base64, pas chiffré
// Exemple de décodage : https://jwt.io
// Résultat visible : { "sub": "123", "password": "secret123", ... }
✅ SÉCURISÉ
// ✅ SÉCURISÉ : Seulement des données non sensibles
const token = jwt.sign({
  sub: user.id,        // ID utilisateur (non sensible)
  email: user.email,   // Email (non sensible, déjà public souvent)
  role: user.role      // Rôle (non sensible, nécessaire pour les permissions)
}, SECRET);

// Règle d'or : Ne jamais mettre de passwords, clés API, numéros de carte, etc.

Règle 2 : Secret fort et long

Le secret doit être suffisamment long et aléatoire pour résister aux attaques par force brute.

❌ MAUVAIS
// ❌ MAUVAIS : Secret trop court et prévisible
const SECRET = 'secret';           // Cracké instantanément
const SECRET = 'mySecret123';      // Cracké en quelques secondes
const SECRET = 'smartcity2024';    // Devinable facilement

// Ces secrets peuvent être crackés par force brute très rapidement
✅ BON
// ✅ BON : Secret cryptographiquement sécurisé (256 bits minimum)
const crypto = require('crypto');

// Générer un secret de 64 bytes (512 bits) = 128 caractères hex
const SECRET = crypto.randomBytes(64).toString('hex');
// Résultat : 'a9f3c5e7b2d4f6a8b1c3d5e7f9a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0...'

// Stocker dans les variables d'environnement
// .env file :
// JWT_SECRET=a9f3c5e7b2d4f6a8b1c3d5e7f9a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0

// JAMAIS dans le code source (même commenté !)
⚠️ Important

Stockez le secret dans les variables d'environnement (.env), jamais dans le code source, même commenté. Utilisez un gestionnaire de secrets en production (AWS Secrets Manager, HashiCorp Vault, etc.).

Règle 3 : Liste blanche des algorithmes

Sans spécifier l'algorithme attendu, vous êtes vulnérable à l'attaque "None algorithm" où l'attaquant envoie un token avec "alg": "none" et aucune signature.

🔴 Attaque "None Algorithm"

Un attaquant peut créer un token avec {"alg": "none"} et modifier le payload à volonté. Sans liste blanche d'algorithmes, certains validateurs acceptent ce token comme valide !

❌ VULNÉRABLE
// ❌ VULNÉRABLE : Pas de liste blanche d'algorithmes
const decoded = jwt.verify(token, SECRET);

// Problème : Si l'attaquant envoie un token avec "alg": "none",
// certains validateurs l'acceptent sans vérifier la signature !
// L'attaquant peut alors modifier le payload à volonté
✅ SÉCURISÉ
// ✅ SÉCURISÉ : Liste blanche explicite des algorithmes acceptés
const decoded = jwt.verify(token, SECRET, {
  algorithms: ['HS256']  // Seulement HS256 accepté
  // Si le token a "alg": "none" ou "RS256", la validation échouera
});

// Toujours spécifier explicitement les algorithmes autorisés
// Pour RS256 : algorithms: ['RS256']
// Pour plusieurs : algorithms: ['HS256', 'RS256']

Règle 4 : Toujours une expiration

Un token sans expiration est un risque de sécurité majeur. Si volé, il reste valide indéfiniment.

❌ Token éternel
// ❌ DANGEREUX : Token sans expiration
const token = jwt.sign({ sub: user.id }, SECRET);

// Problème : Si ce token est volé, l'attaquant a un accès permanent
// Même si l'utilisateur change son mot de passe, le token reste valide
// Impossible de révoquer sans blacklist complète
✅ Token avec expiration
// ✅ SÉCURISÉ : Token avec expiration
const token = jwt.sign(
  { sub: user.id },
  SECRET,
  { expiresIn: '1h' }  // Expire dans 1 heure
);

// Formats acceptés :
// - '15m' : 15 minutes
// - '1h' : 1 heure
// - '7d' : 7 jours
// - 3600 : 3600 secondes

// Si le token est volé, l'attaquant n'a qu'un accès limité dans le temps

Règle 5 : Issuer et Audience

Ces claims empêchent un token destiné à une application d'être utilisé pour une autre. Protection contre la réutilisation de tokens entre différents services.

💡 Pourquoi Issuer et Audience ?

Issuer (iss) : Identifie qui a créé le token. Empêche qu'un token créé par un service malveillant soit accepté par votre API.

Audience (aud) : Identifie pour qui est le token. Empêche qu'un token créé pour l'app mobile soit utilisé pour l'app web, et vice versa.

Exemple complet et sécurisé
// ✅ COMPLET ET SÉCURISÉ : Toutes les règles appliquées
const token = jwt.sign(
  { 
    sub: user.id,        // Règle 1 : Pas de données sensibles
    email: user.email,   // Données non sensibles uniquement
    role: user.role
  },
  process.env.JWT_SECRET,  // Règle 2 : Secret fort depuis .env
  {
    expiresIn: '1h',                    // Règle 4 : Expiration
    issuer: 'smartcity-api',            // Règle 5 : Qui a créé le token
    audience: 'smartcity-web-app'        // Règle 5 : Pour qui est le token
  }
);

// Validation stricte avec toutes les vérifications
const decoded = jwt.verify(token, process.env.JWT_SECRET, {
  issuer: 'smartcity-api',        // Vérifier l'issuer
  audience: 'smartcity-web-app',   // Vérifier l'audience
  algorithms: ['HS256']            // Règle 3 : Liste blanche d'algorithmes
});

// Si l'issuer ou l'audience ne correspondent pas, la validation échouera
// Exemple : un token créé pour 'smartcity-mobile-app' sera rejeté

Résumé des avantages/inconvénients JWT

✅ Checklist de sécurité JWT
  • ✓ Pas de données sensibles dans le payload
  • ✓ Secret fort (256 bits minimum) en variable d'environnement
  • ✓ Liste blanche d'algorithmes explicite
  • ✓ Expiration toujours définie
  • ✓ Issuer et Audience vérifiés
  • ✓ Refresh tokens implémentés pour la révocation
1.7 OAuth 2.0 : La délégation d'autorisation

Ce que OAuth N'EST PAS

⚠️ Important à comprendre

OAuth 2.0 n'est PAS une méthode d'authentification. C'est un protocole de délégation d'autorisation.

OAuth permet à une application tierce d'accéder aux ressources d'un utilisateur sans avoir son mot de passe.

Le problème résolu

Scénario : L'application mobile "EventFinder" veut accéder aux événements favoris de Marie sur SmartCity.

❌ Solution dangereuse

Marie donne son mot de passe SmartCity à EventFinder.

Problèmes :

  • EventFinder a un accès total au compte de Marie
  • Marie ne peut pas révoquer l'accès sans changer son mot de passe
  • Si EventFinder est compromis, le compte de Marie l'est aussi
  • EventFinder peut faire n'importe quoi avec le compte (supprimer des données, changer le mot de passe, etc.)
✅ Solution OAuth

Marie autorise EventFinder via SmartCity, sans jamais donner son mot de passe.

Avantages :

  • Marie peut révoquer l'accès à tout moment
  • EventFinder n'a accès qu'aux permissions accordées (ex: seulement les événements favoris)
  • Si EventFinder est compromis, le compte de Marie reste sécurisé
  • Marie garde le contrôle total sur son compte

Histoire et adoption

  • 2006 : Twitter crée OAuth 1.0 (complexe, basé sur les signatures HMAC)
  • 2010 : Google, Facebook adoptent OAuth pour leurs APIs
  • 2012 : OAuth 2.0 publié (RFC 6749), simplifié et plus facile à implémenter
  • Aujourd'hui : Standard universel utilisé par Google, Facebook, GitHub, Microsoft, Twitter, et des milliers d'autres services

Les 4 rôles OAuth

OAuth définit 4 rôles distincts dans le processus d'autorisation :

┌──────────────┐
│    Marie     │  Resource Owner (utilisatrice finale)
└──────────────┘
       ↓
┌──────────────┐
│ SmartCity    │  Client (application qui veut se connecter via Google)
└──────────────┘
       ↓
┌──────────────┐
│ Google OAuth │  Authorization Server (délivre tokens)
└──────────────┘
       ↓
┌──────────────┐
│ Google APIs  │  Resource Server (profile, email, etc.)
└──────────────┘
1. Resource Owner (Propriétaire de la ressource)

Exemple : Marie, utilisatrice qui souhaite créer un compte SmartCity avec son identité Google.

C'est elle qui possède la ressource (ses informations Google) et qui autorise le partage via le consentement OAuth.

2. Client (Application tierce)

Exemple : SmartCity

L'application SmartCity souhaite importer les informations de Marie depuis Google pour accélérer l'inscription. Elle redirige Marie vers Google, récupère le code d'autorisation puis échange ce code contre un access token.

3. Authorization Server (Serveur d'autorisation)

Exemple : Google OAuth 2.0

Google authentifie Marie, lui affiche l'écran de consentement, puis délivre à SmartCity un code d'autorisation, un access token et éventuellement un refresh token.

4. Resource Server (Serveur de ressources)

Exemple : Google People API

Ce serveur expose les données protégées (profil, email). SmartCity l'appelle avec l'access token pour récupérer les informations de Marie et compléter son inscription.

💡 En pratique

Selon les besoins, l'Authorization Server et le Resource Server peuvent être distincts (comme Google OAuth + Google People API) ou combinés au sein d'un même fournisseur d'identité.

⚠️ Clarification essentielle

OAuth 2.0 encadre l'autorisation déléguée : il délivre à SmartCity un droit d'accès limité aux données de Marie. L'authentification de Marie est réalisée par Google. Pour récupérer de façon standardisée l'identité vérifiée (nom, email, photo), on ajoute souvent OpenID Connect au-dessus d'OAuth 2.0.

  scope: ['openid', 'email', 'profile']
};

  const params = new URLSearchParams({
    client_id: config.clientId,
    redirect_uri: config.redirectUri,
    response_type: 'code',
    scope: config.scope.join(' '),
    state,
    access_type: 'offline', // refresh token
    prompt: 'consent'
  });

// Endpoint token pour client credentials
app.post('/oauth/token', async (req, res) => {
  const { grant_type, client_id, client_secret, scope } = req.body;
  
  if (grant_type === 'client_credentials') {
    // 1. Valider le client (vérifier client_id et client_secret)
    const client = clients.get(client_id);
    if (!client || client.secret !== client_secret) {
      return res.status(401).json({ error: 'invalid_client' });
    }

    // Pas d'utilisateur, donc pas besoin de refresh token

      },

      { expiresIn: '1h' }
    );

      token_type: 'Bearer',
      expires_in: 3600,
      scope: scope
    });

Flow 3 : PKCE (Protection pour apps mobiles)

Le problème : Les applications mobiles natives ne peuvent pas garder un client_secret sécurisé car le code peut être décompilé.

PKCE (Proof Key for Code Exchange, prononcé "pixie") résout ce problème.

Principe
1. App génère un code_verifier aléatoire (43-128 caractères)
   code_verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"

2. App calcule code_challenge
   code_challenge = Base64URL(SHA256(code_verifier))
   code_challenge = "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"

3. Authorization request avec code_challenge
   /authorize?code_challenge=E9Melhoa...&code_challenge_method=S256

4. Token request avec code_verifier
   /token avec code_verifier=dBjftJeZ...
   
5. Serveur vérifie : SHA256(code_verifier) == code_challenge
Implémentation côté client (React Native)
import * as Crypto from 'expo-crypto';
import * as AuthSession from 'expo-auth-session';

async function loginWithOAuth() {
  // 1. Générer code_verifier (aléatoire, 43-128 caractères)
  const codeVerifier = AuthSession.generateCodeVerifier(128);
  
  // 2. Calculer code_challenge (hash SHA256 du verifier)
  const codeChallenge = await Crypto.digestStringAsync(
    Crypto.CryptoDigestAlgorithm.SHA256,
    codeVerifier,
    { encoding: Crypto.CryptoEncoding.BASE64 }
  );
  
  // 3. Rediriger vers authorization endpoint avec code_challenge
  const authUrl = `https://auth.smartcity.local/oauth/authorize?` +
    `client_id=mobile_app&` +
    `redirect_uri=${encodeURIComponent('myapp://callback')}&` +
    `response_type=code&` +
    `code_challenge=${codeChallenge}&` +           // Le challenge (hash)
    `code_challenge_method=S256&` +                // Méthode : SHA256
    `scope=read:events write:favorites`;
  
  const result = await AuthSession.startAsync({ authUrl });
  
  // 4. Échanger code contre token (avec code_verifier)
  if (result.type === 'success') {
    const tokenResponse = await fetch('https://auth.smartcity.local/oauth/token', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        grant_type: 'authorization_code',
        code: result.params.code,
        client_id: 'mobile_app',
        redirect_uri: 'myapp://callback',
        code_verifier: codeVerifier  // Le verifier original (pas de client_secret !)
      })
    });
    
    const tokens = await tokenResponse.json();
    return tokens.access_token;
  }
}

// Vérifier code_verifier lors de l'échange
app.post('/oauth/token', (req, res) => {
  const { code, code_verifier } = req.body;
  
  const codeData = authCodes.get(code);
  
  // Si PKCE est utilisé, vérifier le code_verifier
  if (codeData.codeChallenge) {
    // Calculer le challenge à partir du verifier
    let computedChallenge;
    if (codeData.codeChallengeMethod === 'S256') {
      // SHA256 du verifier, puis Base64URL
      computedChallenge = crypto
        .createHash('sha256')
        .update(code_verifier)
        .digest('base64')
        .replace(/\+/g, '-')    // Base64URL encoding
        .replace(/\//g, '_')
        .replace(/=/g, '');
    } else {
      // Plain text (moins sécurisé)
      computedChallenge = code_verifier;
    }
    
    // Vérifier que le challenge calculé correspond au challenge stocké
    if (computedChallenge !== codeData.codeChallenge) {
      return res.status(400).json({
        error: 'invalid_grant',
        error_description: 'Code verifier mismatch'
      });
    }
  }
  
  // Si la vérification passe, continuer avec la génération du token...
});
✅ Avantages de PKCE
  • Pas besoin de client_secret : L'app mobile n'a pas besoin de stocker un secret
  • Protection contre interception du code : Même si le code est intercepté, il ne peut pas être utilisé sans le code_verifier
  • Recommandé pour toutes les apps publiques : Mobiles, SPAs (Single Page Applications), etc.

1.11 Révocabilité des méthodes d'authentification

Révoquer un accès consiste à empêcher un utilisateur ou une application de continuer à consommer l’API après compromission ou retrait d’autorisation. Chaque méthode implique un compromis entre rapidité de révocation et coût en requêtes :

🔐 Basic Auth (username/password envoyés à chaque requête)
  • Révocation : changer ou désactiver le mot de passe dans la base.
  • Délai : immédiat après modification (car chaque requête vérifie la DB).
  • Coût : 1 requête DB par appel.
  • Limites : aucune granularité (toutes les requêtes sont coupées d’un coup), UX médiocre.
🔑 API Keys (clé opaque stockée côté serveur)
  • Révocation : supprimer ou désactiver la clé dans la base.
  • Délai : immédiat (validation en base à chaque requête ou via cache court).
  • Coût : 1 requête DB/cache par appel.
  • Bonnes pratiques : clés multiples par client pour révoquer finement.
🎟 Sessions serveurs (cookies + store)
  • Révocation : supprimer la session du store (Redis, base).
  • Délai : immédiat (toutes les requêtes vérifient la session).
  • Coût : 1 requête store par appel (souvent redis, mémoire).
  • Atout : expiration contrôlée côté serveur, logout simple.
🤝 OAuth 2.0 / OpenID Connect (provider externe)
  • Révocation : côté provider (Google, LinkedIn) via leurs endpoints.
  • Délai : immédiat côté provider, nécessite parfois de révoquer aussi la session locale.
  • Coût : dépend du provider (révocation d’un refresh token, invalidation d’un consentement).
  • Point clé : conserver la capacité de désactiver le compte côté SmartCity si nécessaire.
🚫 JWT pur (stateless)
  • Révocation : impossible avant expiration naturelle du token.
  • Délai : dépend uniquement de exp (ex : 1h, 24h).
  • Coût : 0 requête DB par validation (signature cryptographique).
  • Usage : accélère les lectures mais ne convient pas aux contextes exigeant une coupure immédiate.
📝 JWT + Blacklist
  • Révocation : ajouter le token compromis dans une liste noire côté serveur.
  • Délai : immédiat, mais nécessite de vérifier la blacklist à chaque requête (retour au coût d’une requête DB/cache).
  • Compromis : permet la coupure rapide mais supprime l’intérêt “stateless”.
  • Bonnes pratiques : TTL court, purge des tokens expirés.
✅ Synthèse opérationnelle
  • Identifier les accès qui nécessitent une révocation instantanée (admin, partenaires sensibles) → préférer API keys, sessions, OAuth avec store.
  • Pour les appels très fréquents et peu risqués → JWT stateless + expiration courte, éventuellement couplé à un refresh token.
  • Ne jamais oublier la révocation côté provider lorsqu’on délègue l’authentification (Google, GitHub).
  • Documenter la procédure de rotation des clés/tokens et l’automatiser autant que possible.

6 sous-parties
2.1 Authentification vs Autorisation : La différence critique

Il est crucial de comprendre la différence entre authentification et autorisation. Ces deux concepts sont souvent confondus mais sont fondamentalement différents.

Authentification

"Qui êtes-vous ?"

Vérifie l'identité de l'utilisateur. Exemple : Marie se connecte avec son email/password.

Autorisation

"Que pouvez-vous faire ?"

Vérifie les permissions de l'utilisateur. Exemple : Marie peut-elle supprimer cet événement ?

🔴 Erreur classique

Vérifier l'authentification mais oublier l'autorisation. C'est une vulnérabilité critique qui permet à n'importe quel utilisateur connecté d'effectuer des actions qu'il ne devrait pas pouvoir faire.

Exemple de vulnérabilité

Voici un exemple typique d'une route qui vérifie l'authentification mais oublie l'autorisation :

❌ VULNÉRABILITÉ
// ❌ VULNÉRABILITÉ : Vérifie juste qu'on est connecté
// Problème : N'importe quel utilisateur connecté peut supprimer N'IMPORTE QUEL événement !
app.delete('/api/events/:id', authenticateJWT, async (req, res) => {
  // Seulement vérifie que l'utilisateur est authentifié
  // Ne vérifie PAS si c'est le créateur de l'événement ou un admin
  await prisma.event.delete({ where: { id: req.params.id } });
  res.status(204).send();
});

// Conséquence : 
// - Alice (utilisateur normal) peut supprimer l'événement de Bob
// - N'importe qui peut supprimer n'importe quel événement
// - Vulnérabilité critique de sécurité !
✅ SÉCURISÉ
// ✅ SÉCURISÉ : Vérifie les permissions
app.delete('/api/events/:id', authenticateJWT, async (req, res) => {
  // 1. Récupérer l'événement depuis la base de données
  const event = await prisma.event.findUnique({ 
    where: { id: req.params.id } 
  });
  
  if (!event) {
    return res.status(404).json({ error: 'Event not found' });
  }
  
  // 2. Vérifier les permissions : est-ce le créateur OU un admin ?
  // req.user.sub = ID de l'utilisateur connecté (depuis le JWT)
  // event.creatorId = ID du créateur de l'événement
  // req.user.role = Rôle de l'utilisateur (depuis le JWT)
  if (event.creatorId !== req.user.sub && req.user.role !== 'admin') {
    // 3. Si pas autorisé, renvoyer 403 Forbidden
    return res.status(403).json({ 
      error: 'Forbidden',
      message: 'You do not have permission to delete this event'
    });
  }
  
  // 4. Si autorisé, supprimer l'événement
  await prisma.event.delete({ where: { id: req.params.id } });
  res.status(204).send();
});

// Sécurité :
// - Seul le créateur peut supprimer son événement
// - Les admins peuvent supprimer n'importe quel événement
// - Les autres utilisateurs reçoivent une erreur 403

Principe du moindre privilège

✅ Principe du moindre privilège

Donnez uniquement les permissions nécessaires, rien de plus.

  • Un utilisateur normal ne devrait avoir accès qu'à ses propres ressources
  • Un modérateur peut avoir des permissions supplémentaires mais limitées
  • Seuls les admins devraient avoir des permissions étendues
  • Chaque action doit être vérifiée : "Cet utilisateur a-t-il le droit de faire cela ?"
💡 Checklist de sécurité

Pour chaque endpoint qui modifie ou supprime des données, posez-vous ces questions :

  • ✓ L'utilisateur est-il authentifié ? (middleware authenticateJWT)
  • ✓ L'utilisateur a-t-il le droit d'effectuer cette action ? (vérification d'autorisation)
  • ✓ Est-ce que l'utilisateur est le propriétaire de la ressource ?
  • ✓ Ou est-ce que l'utilisateur a un rôle qui lui donne cette permission ?
  • ✓ Le code renvoie-t-il une erreur 403 si l'utilisateur n'est pas autorisé ?
2.2 RBAC (Role-Based Access Control)

Principe de fonctionnement

Les permissions sont attachées à des rôles, et les utilisateurs ont un ou plusieurs rôles.

┌──────────┐     ┌────────────┐     ┌─────────────────┐
│   User   │ ──→ │    Role    │ ──→ │  Permissions    │
└──────────┘     └────────────┘     └─────────────────┘
   Marie    →    organizer    →    create:events
                                    update:own_events
                                    delete:own_events
✅ Avantages
  • Simple à comprendre et implémenter
  • Facile à auditer ("qui a quel rôle ?")
  • Bon pour la plupart des applications
❌ Inconvénients
  • Peut devenir rigide avec beaucoup de cas particuliers
  • Explosion de rôles si trop de nuances

Définition des rôles et permissions

Pour SmartCity, voici une hiérarchie classique :

const roles = {
  // Citoyen lambda : permissions de base
  citizen: [
    'read:events',              // Lire les événements publics
    'read:own_profile',         // Lire son propre profil
    'update:own_profile',       // Modifier son propre profil
    'create:registration',      // S'inscrire à un événement
    'delete:own_registration'  // Se désinscrire d'un événement
  ],
  
  // Organisateur d'événements : peut créer et gérer ses événements
  organizer: [
    'read:events',              // Lire tous les événements
    'create:events',            // Créer de nouveaux événements
    'update:own_events',        // Modifier ses propres événements
    'delete:own_events',        // Supprimer ses propres événements
    'read:event_stats',         // Voir les statistiques de ses événements
    'read:own_profile',         // Lire son propre profil
    'update:own_profile'        // Modifier son propre profil
  ],
  
  // Modérateur : peut gérer tous les événements et utilisateurs
  moderator: [
    'read:events',              // Lire tous les événements
    'read:all_events',          // Accès complet à tous les événements
    'update:any_events',        // Modifier n'importe quel événement
    'read:users',               // Lire les informations des utilisateurs
    'suspend:users'             // Suspendre des utilisateurs
  ],
  
  // Administrateur : tous les pouvoirs (wildcard)
  admin: [
    'manage:all'  // Wildcard : peut tout faire (bypass toutes les vérifications)
  ]
};

Implémentation basique

Middleware simple pour vérifier les permissions requises :

// Middleware : vérifier qu'un utilisateur a les permissions requises
function authorize(...requiredPermissions) {
  return (req, res, next) => {
    // 1. Récupérer les permissions du rôle de l'utilisateur
    // req.user.role est défini par le middleware authenticateJWT
    const userPermissions = roles[req.user.role] || [];
    
    // 2. Cas spécial : admin a tout (bypass)
    if (userPermissions.includes('manage:all')) {
      return next();  // Admin peut tout faire, pas besoin de vérifier
    }
    
    // 3. Vérifier que l'utilisateur a TOUTES les permissions requises
    // every() retourne true seulement si TOUTES les permissions sont présentes
    const hasAllPermissions = requiredPermissions.every(permission =>
      userPermissions.includes(permission)
    );
    
    // 4. Si pas toutes les permissions, renvoyer 403 Forbidden
    if (!hasAllPermissions) {
      return res.status(403).json({
        error: 'Forbidden',
        message: 'Insufficient permissions',
        required: requiredPermissions,      // Permissions demandées
        user_has: userPermissions          // Permissions de l'utilisateur
      });
    }
    
    // 5. Si toutes les permissions sont présentes, continuer
    next();
  };
}

// Utilisation sur les routes
// Exemple 1 : Créer un événement (nécessite create:events)
app.post('/api/events',
  authenticateJWT,              // 1. Vérifier l'authentification
  authorize('create:events'),    // 2. Vérifier la permission
  async (req, res) => {
    const event = await prisma.event.create({
      data: {
        ...req.body,
        creatorId: req.user.sub  // ID de l'utilisateur connecté
      }
    });
    res.status(201).json(event);
  }
);

// Exemple 2 : Supprimer n'importe quel événement (nécessite delete:any_events)
app.delete('/api/events/:id',
  authenticateJWT,
  authorize('delete:any_events'),  // Seuls les modérateurs/admins ont cette permission
  async (req, res) => {
    await prisma.event.delete({ where: { id: req.params.id } });
    res.status(204).send();
  }
);

Gestion des permissions "own" (ses propres ressources)

Souvent, un utilisateur peut modifier ses propres ressources mais pas celles des autres. Cela nécessite une logique plus complexe :

// Logique : delete SON propre événement OU être admin/moderator
app.delete('/api/events/:id', authenticateJWT, async (req, res) => {
  // 1. Récupérer l'événement depuis la base de données
  const event = await prisma.event.findUnique({ 
    where: { id: req.params.id } 
  });
  
  if (!event) {
    return res.status(404).json({ error: 'Event not found' });
  }
  
  // 2. Récupérer les permissions du rôle de l'utilisateur
  const userPermissions = roles[req.user.role];
  
  // 3. Vérifier les permissions avec logique OU :
  //    - Admin peut tout faire (manage:all)
  //    - Moderator peut supprimer n'importe quel événement (delete:any_events)
  //    - Organizer peut supprimer SES propres événements (delete:own_events + ownership)
  const canDelete =
    userPermissions.includes('manage:all') ||                    // Admin
    userPermissions.includes('delete:any_events') ||             // Moderator
    (userPermissions.includes('delete:own_events') &&            // Organizer
     event.creatorId === req.user.sub);                          // ET c'est son événement
  
  // 4. Si pas autorisé, renvoyer 403
  if (!canDelete) {
    return res.status(403).json({
      error: 'Forbidden',
      message: 'You can only delete your own events'
    });
  }
  
  // 5. Si autorisé, supprimer l'événement
  await prisma.event.delete({ where: { id: req.params.id } });
  res.status(204).send();
});

Middleware réutilisable pour "own resources"

Pour éviter de répéter cette logique partout, créons un helper générique :

// Helper : vérifier ownership ou permission globale
// Ce middleware est réutilisable pour n'importe quelle ressource
function authorizeResource(options) {
  const { 
    permission,           // Permission globale (ex: 'delete:any_events')
    ownPermission,        // Permission propres ressources (ex: 'delete:own_events')
    getResource,          // Fonction pour récupérer la ressource depuis la DB
    getOwnerId           // Fonction pour extraire l'owner ID de la ressource
  } = options;
  
  return async (req, res, next) => {
    const userPermissions = roles[req.user.role] || [];
    
    // 1. Admin bypass : si admin, autoriser directement
    if (userPermissions.includes('manage:all')) {
      return next();
    }
    
    // 2. Permission globale : si l'utilisateur a la permission globale, autoriser
    // Exemple : moderator avec 'delete:any_events' peut supprimer n'importe quel événement
    if (permission && userPermissions.includes(permission)) {
      return next();
    }
    
    // 3. Permission sur propres ressources : vérifier l'ownership
    if (ownPermission && userPermissions.includes(ownPermission)) {
      // Charger la ressource depuis la base de données
      const resource = await getResource(req);
      
      if (!resource) {
        return res.status(404).json({ error: 'Resource not found' });
      }
      
      // Vérifier que l'utilisateur est le propriétaire
      const ownerId = getOwnerId(resource);
      if (ownerId === req.user.sub) {
        // Attacher la ressource à req pour éviter de la re-fetch dans le handler
        req.resource = resource;
        return next();
      }
    }
    
    // 4. Si aucune condition n'est remplie, refuser l'accès
    res.status(403).json({
      error: 'Forbidden',
      message: 'Insufficient permissions'
    });
  };
}

// Utilisation simplifiée
app.delete('/api/events/:id',
  authenticateJWT,
  authorizeResource({
    permission: 'delete:any_events',        // Permission globale (moderator)
    ownPermission: 'delete:own_events',     // Permission propres ressources (organizer)
    getResource: async (req) => {
      // Fonction pour récupérer l'événement
      return await prisma.event.findUnique({ 
        where: { id: req.params.id } 
      });
    },
    getOwnerId: (event) => event.creatorId  // Fonction pour extraire l'owner ID
  }),
  async (req, res) => {
    // req.resource contient déjà l'événement (pas besoin de re-fetch)
    // C'est plus efficace car on évite une requête DB supplémentaire
    await prisma.event.delete({ where: { id: req.params.id } });
    res.status(204).send();
  }
);

RBAC hiérarchique

Parfois, vous voulez que certains rôles "héritent" des permissions d'autres rôles. Cela évite la duplication de permissions :

// Définir la hiérarchie des rôles
const roleHierarchy = {
  citizen: [],                    // Pas de parent
  organizer: ['citizen'],         // Hérite de citizen (donc a toutes les permissions de citizen)
  moderator: ['organizer'],       // Hérite de organizer (donc aussi de citizen)
  admin: ['moderator']            // Hérite de moderator (donc de tout)
};

// Fonction pour obtenir TOUTES les permissions (avec héritage)
function getAllPermissions(role) {
  // 1. Récupérer les permissions directes du rôle
  const directPermissions = roles[role] || [];
  
  // 2. Récupérer les rôles parents (ceux dont ce rôle hérite)
  const inheritedRoles = roleHierarchy[role] || [];
  
  // 3. Récupérer récursivement les permissions des rôles parents
  // flatMap() permet de "aplatir" les tableaux de permissions
  const inheritedPermissions = inheritedRoles.flatMap(parentRole => 
    getAllPermissions(parentRole)  // Récursion : obtenir les permissions du parent
  );
  
  // 4. Fusionner et dédupliquer les permissions
  // new Set() supprime les doublons
  return [...new Set([...directPermissions, ...inheritedPermissions])];
}

// Exemple d'utilisation :
// getAllPermissions('moderator') retourne :
// - Les permissions directes de moderator
// - Les permissions de organizer (parent)
// - Les permissions de citizen (parent de organizer)

// Utilisation dans le middleware authorize
function authorize(...requiredPermissions) {
  return (req, res, next) => {
    // Obtenir TOUTES les permissions (directes + héritées)
    const allPermissions = getAllPermissions(req.user.role);
    
    // Admin bypass
    if (allPermissions.includes('manage:all')) {
      return next();
    }
    
    // Vérifier que l'utilisateur a TOUTES les permissions requises
    const hasAllPermissions = requiredPermissions.every(perm =>
      allPermissions.includes(perm)
    );
    
    if (!hasAllPermissions) {
      return res.status(403).json({ error: 'Forbidden' });
    }
    
    next();
  };
}
✅ Avantages du RBAC hiérarchique
  • Évite la duplication : Pas besoin de répéter les permissions de base dans chaque rôle
  • Maintenance facilitée : Modifier une permission de base affecte automatiquement tous les rôles qui en héritent
  • Logique claire : La hiérarchie reflète la structure organisationnelle
2.3 ABAC (Attribute-Based Access Control)

Principe de fonctionnement

Les décisions d'autorisation sont basées sur des attributs (propriétés) plutôt que sur des rôles fixes.

Attributs considérés :
Utilisateur

rôle, département, ancienneté, localisation

Ressource

type, statut, propriétaire, sensibilité

Action

lecture, écriture, suppression

Contexte

heure, localisation, appareil

Exemple de règle ABAC :
Un organisateur peut supprimer un événement SI :
- L'événement lui appartient
- ET l'événement n'a pas encore commencé
- ET il y a moins de 10 inscriptions
✅ Avantages
  • Très flexible et granulaire
  • Gère des logiques métier complexes
  • S'adapte à des contextes changeants
❌ Inconvénients
  • Plus complexe à implémenter et déboguer
  • Peut être lent si mal optimisé
  • Difficile à auditer ("pourquoi Marie peut-elle faire ça ?")

Implémentation avec CASL

  if (user.role === 'organizer') {
    // Permissions de base
    can('read', 'Event');      // Peut lire tous les événements
    can('create', 'Event');     // Peut créer des événements
    
    // Peut modifier/supprimer SES événements (vérification d'attribut)
    can('update', 'Event', { creatorId: user.id });
    can('delete', 'Event', { creatorId: user.id });
    
    // MAIS PAS les événements passés (règle basée sur l'attribut startDate)
    cannot('delete', 'Event', { 
      startDate: { $lt: new Date() }  // startDate < maintenant = événement passé
    });
    
    // MAIS PAS si + de 50 inscriptions (règle basée sur l'attribut registrationCount)
    cannot('delete', 'Event', { 
      registrationCount: { $gt: 50 }  // Trop d'inscriptions = trop d'impact
    });
    
    // Peut lire les inscriptions de SES événements
    can('read', 'Registration', { eventCreatorId: user.id });
  }
  
  // Citizen : permissions limitées
  if (user.role === 'citizen') {
    can('read', 'Event');                              // Lire les événements
    can('create', 'Registration');                     // S'inscrire à un événement
    can('delete', 'Registration', { userId: user.id }); // Se désinscrire
    can('read', 'Profile', { userId: user.id });       // Lire son profil
    can('update', 'Profile', { userId: user.id });     // Modifier son profil
  }
  
  return build();
}

Middleware d'autorisation

function checkAbility(action, subject) {
  return async (req, res, next) => {
    // 1. Créer l'ability pour l'utilisateur connecté
    const ability = defineAbilitiesFor(req.user);
    
    // 2. Cas 1 : Vérifier sur un type générique (sans ID)
    // Exemple : POST /api/events (création)
    if (!req.params.id) {
      if (!ability.can(action, subject)) {
        return res.status(403).json({ 
          error: 'Forbidden',
          message: `Cannot ${action} ${subject}`
        });
      }
      return next();
    }
    
    // 3. Cas 2 : Vérifier sur une ressource spécifique (avec ID)
    // Exemple : DELETE /api/events/123 (suppression d'un événement spécifique)
    let resource;
    if (subject === 'Event') {
      // Récupérer l'événement avec ses relations
      resource = await prisma.event.findUnique({ 
        where: { id: req.params.id },
        include: { 
          _count: { select: { registrations: true } }  // Compter les inscriptions
        }
      });
      
      // Ajouter le count comme attribut pour les règles ABAC
      if (resource) {
        resource.registrationCount = resource._count.registrations;
      }
    }
    
    if (!resource) {
      return res.status(404).json({ error: 'Resource not found' });
    }
    
    // 4. Vérifier avec l'instance concrète (tous les attributs sont disponibles)
    // CASL va vérifier toutes les règles : creatorId, startDate, registrationCount, etc.
    if (!ability.can(action, resource)) {
      return res.status(403).json({ 
        error: 'Forbidden',
        message: `Cannot ${action} this ${subject}`
      });
    }
    
    // 5. Attacher la ressource à req pour éviter re-fetch dans le handler
    req.resource = resource;
    next();
  };
}

// Utilisation simplifiée
app.delete('/api/events/:id',
  authenticateJWT,                    // 1. Vérifier l'authentification
  checkAbility('delete', 'Event'),     // 2. Vérifier l'autorisation ABAC
  async (req, res) => {
    // req.resource contient déjà l'événement (pas besoin de re-fetch)
    await prisma.event.delete({ where: { id: req.params.id } });
    res.status(204).send();
  }
);

Règles contextuelles avancées

ABAC permet des règles basées sur le contexte (heure, localisation, appareil, etc.) :

function defineAbilitiesFor(user, context = {}) {
  const { can, cannot, build } = new AbilityBuilder(Ability);
  
  // Règle temporelle : modifications seulement en heures de bureau
  if (user.role === 'organizer') {
    can('create', 'Event');
    
    // Récupérer l'heure actuelle depuis le contexte
    const hour = context.currentTime?.getHours() || new Date().getHours();
    
    // Seulement entre 9h et 18h
    if (hour >= 9 && hour <= 18) {
      can('update', 'Event', { creatorId: user.id });
    } else {
      cannot('update', 'Event');  // Bloqué en dehors des heures de bureau
    }
  }
  
  // Règle de localisation : accès restreint selon pays
  // Exemple : données sensibles seulement accessibles depuis la France
  if (context.country !== 'FR') {
    cannot('read', 'SensitiveData');
  }
  
  // Règle sur appareil : actions sensibles sur desktop uniquement
  // Exemple : suppression d'événements interdite depuis mobile (sécurité)
  if (context.deviceType === 'mobile') {
    cannot('delete', 'Event');
  }
  
  return build();
}

  req.context = {

✅ Quand utiliser ABAC vs RBAC ?
  • RBAC : Parfait pour la plupart des applications avec des rôles simples (user, admin, moderator)
  • ABAC : Idéal quand vous avez besoin de règles complexes basées sur :
    • Les attributs des ressources (date, statut, nombre d'inscriptions)
    • Le contexte (heure, localisation, appareil)
    • Des conditions métier complexes (ex: "peut supprimer si moins de 10 inscriptions ET pas encore commencé")
2.4 Scopes OAuth : Autorisation granulaire

Quand votre API est utilisée par des applications tierces via OAuth, les scopes définissent ce que l'application peut faire au nom de l'utilisateur.

💡 Concept des scopes

Les scopes permettent à l'utilisateur de choisir précisément quelles permissions il accorde à une application tierce. Par exemple, une app peut demander seulement read:events sans avoir accès au profil complet de l'utilisateur.

Définition des scopes

Les scopes suivent généralement le format action:resource :

const validScopes = {
  // Événements
  'read:events': 'Voir les événements publics',
  'read:own_events': 'Voir vos événements',
  'write:events': 'Créer et modifier des événements',
  'delete:events': 'Supprimer des événements',
  
  // Favoris
  'read:favorites': 'Voir vos événements favoris',
  'write:favorites': 'Ajouter des favoris',
  
  // Profil
  'read:profile': 'Voir votre profil',
  'write:profile': 'Modifier votre profil',
  
  // Admin (scopes spéciaux pour les applications admin)
  'admin:users': 'Gérer tous les utilisateurs',
  'admin:events': 'Gérer tous les événements'
};

// Format : action:resource
// - action : read, write, delete, admin
// - resource : events, favorites, profile, users

Middleware de vérification des scopes

Middleware pour vérifier que le token OAuth contient les scopes requis :

function requireScope(...requiredScopes) {
  return (req, res, next) => {
    // 1. Extraire les scopes du token JWT
    // Les scopes sont stockés dans req.user.scope (défini lors de la création du token OAuth)
    // Format : "read:events write:favorites" (chaîne avec espaces)
    const tokenScopes = req.user.scope ? req.user.scope.split(' ') : [];
    
    // 2. Vérifier que le token a TOUS les scopes requis
    // every() retourne true seulement si TOUS les scopes sont présents
    const hasAllScopes = requiredScopes.every(scope =>
      tokenScopes.includes(scope)
    );
    
    // 3. Si pas tous les scopes, renvoyer erreur 403 avec code spécial
    if (!hasAllScopes) {
      return res.status(403).json({
        error: 'insufficient_scope',  // Code d'erreur OAuth standard
        message: 'Token does not have required scopes',
        required: requiredScopes,      // Scopes demandés
        provided: tokenScopes          // Scopes présents dans le token
      });
    }
    
    // 4. Si tous les scopes sont présents, continuer
    next();
  };
}

Combiner rôles et scopes

Dans la réalité, vous combinez souvent les rôles utilisateur ET les scopes OAuth pour une sécurité renforcée :

function checkPermission(action, resource) {
  return async (req, res, next) => {
    // 1. Vérifier le scope OAuth (si token OAuth)
    // Les tokens OAuth ont un champ 'scope', les tokens internes non
    if (req.user.scope) {
      // Construire le scope requis : action:resource
      const requiredScope = `${action}:${resource}`;
      const tokenScopes = req.user.scope.split(' ');
      
      // Vérifier que le token OAuth a le scope requis
      if (!tokenScopes.includes(requiredScope)) {
        return res.status(403).json({
          error: 'insufficient_scope',
          required: requiredScope,
          message: 'OAuth token does not have required scope'
        });
      }
    }
    
    // 2. Vérifier le rôle utilisateur (pour les tokens internes ou en plus)
    // getAllPermissions() récupère toutes les permissions du rôle (avec héritage)
    const userPermissions = getAllPermissions(req.user.role);
    const requiredPermission = `${action}:${resource}`;
    
    // Vérifier que l'utilisateur a la permission via son rôle
    // OU qu'il est admin (manage:all)
    if (!userPermissions.includes(requiredPermission) && 
        !userPermissions.includes('manage:all')) {
      return res.status(403).json({
        error: 'Forbidden',
        message: 'User role does not have required permission'
      });
    }
    
    // 3. Si les deux vérifications passent, continuer
    next();
  };
}

// Utilisation : double vérification
// Le token OAuth doit avoir le scope ET l'utilisateur doit avoir le rôle
app.delete('/api/events/:id',
  authenticateJWT,
  checkPermission('delete', 'events'),  // Vérifie scope ET rôle
  async (req, res) => {
    // Double vérification passée :
    // - Le token OAuth a le scope 'delete:events'
    // - L'utilisateur a le rôle avec la permission 'delete:events'
    await prisma.event.delete({ where: { id: req.params.id } });
    res.status(204).send();
  }
);
⚠️ Pourquoi combiner rôles et scopes ?
  • Sécurité renforcée : Même si un scope est accordé, l'utilisateur doit avoir le rôle correspondant
  • Flexibilité : Les apps tierces demandent des scopes, mais les permissions réelles viennent du rôle
  • Révocation : Si un rôle change, les tokens OAuth existants perdent automatiquement leurs permissions
✅ Bonnes pratiques pour les scopes
  • Granularité : Créez des scopes spécifiques plutôt que des scopes trop larges
  • Documentation : Documentez clairement ce que chaque scope permet
  • Validation : Validez les scopes demandés lors de la requête d'autorisation OAuth
  • Principe du moindre privilège : Les apps tierces ne devraient demander que les scopes nécessaires
2.5 Gestion des permissions en base de données

Même sur une application de taille modeste, externaliser rôles et permissions dans un stockage persistant évite de redéployer au moindre ajustement. On peut certes démarrer avec un simple fichier de configuration, mais l'intérêt reste limité : pas de synchronisation multi-serveurs, pas d'audit et un risque d’oubli lors des déploiements. Très vite, la base de données devient la solution naturelle pour centraliser et faire évoluer ces règles.

💡 Pourquoi stocker en base ?
  • Permissions personnalisées : Donner des permissions spécifiques à certains utilisateurs sans créer de nouveaux rôles
  • Permissions temporaires : Accorder des permissions avec expiration automatique
  • Flexibilité : Modifier les permissions sans redéployer le code
  • Audit : Traçabilité complète de qui a quelles permissions et quand

Schéma de base de données

Structure Prisma pour gérer les permissions de manière flexible :

model User {
  id        String   @id @default(uuid())
  email     String   @unique
  role      Role     @default(CITIZEN)  // Rôle de base (RBAC)
  
  // Permissions custom : permet d'ajouter des permissions spécifiques
  // au-delà du rôle de base
  permissions UserPermission[]
}

enum Role {
  CITIZEN      // Rôle par défaut
  ORGANIZER    // Organisateur d'événements
  MODERATOR    // Modérateur
  ADMIN        // Administrateur
}

model Permission {
  id          String   @id @default(uuid())
  name        String   @unique  // Ex: "delete:any_events", "read:stats"
  description String   // Description de ce que la permission permet
  
  // Relation many-to-many avec les utilisateurs
  users       UserPermission[]
}

model UserPermission {
  id           String     @id @default(uuid())
  userId       String     // ID de l'utilisateur
  permissionId String     // ID de la permission
  granted      Boolean    @default(true)  // true = accordée, false = révoquée
  expiresAt    DateTime?  // Permission temporaire (null = permanente)
  
  // Relations
  user         User       @relation(fields: [userId], references: [id])
  permission   Permission @relation(fields: [permissionId], references: [id])
  
  // Un utilisateur ne peut avoir qu'une seule entrée par permission
  @@unique([userId, permissionId])
}

Récupération des permissions

Fonction pour récupérer toutes les permissions d'un utilisateur (rôle + permissions custom) :

async function getUserPermissions(userId) {
  // 1. Récupérer l'utilisateur avec ses permissions custom
  const user = await prisma.user.findUnique({
    where: { id: userId },
    include: {
      permissions: {
        // Filtrer seulement les permissions accordées et non expirées
        where: {
          granted: true,  // Seulement les permissions accordées
          OR: [
            { expiresAt: null },                    // Permissions permanentes
            { expiresAt: { gt: new Date() } }      // Permissions non expirées
          ]
        },
        include: {
          permission: true  // Inclure les détails de la permission
        }
      }
    }
  });
  
  // 2. Permissions de base du rôle (depuis le code)
  // roles est l'objet défini précédemment avec les permissions par rôle
  const rolePermissions = roles[user.role] || [];
  
  // 3. Permissions custom de l'utilisateur (depuis la DB)
  // Extraire les noms des permissions depuis les relations
  const customPermissions = user.permissions.map(up => up.permission.name);
  
  // 4. Fusionner et dédupliquer les permissions
  // new Set() supprime les doublons
  return [...new Set([...rolePermissions, ...customPermissions])];
}

// Middleware utilisant les permissions DB
function authorize(...requiredPermissions) {
  return async (req, res, next) => {
    // Récupérer toutes les permissions (rôle + custom) depuis la DB
    const userPermissions = await getUserPermissions(req.user.sub);
    
    // Admin bypass
    if (userPermissions.includes('manage:all')) {
      return next();
    }
    
    // Vérifier que l'utilisateur a TOUTES les permissions requises
    const hasAllPermissions = requiredPermissions.every(perm =>
      userPermissions.includes(perm)
    );
    
    if (!hasAllPermissions) {
      return res.status(403).json({ error: 'Forbidden' });
    }
    
    next();
  };
}

app.post('/api/admin/users/:userId/permissions',
  authenticateJWT,
  authorize('manage:permissions'),  // Seuls les admins peuvent gérer les permissions
  async (req, res) => {
    const { permissionName, expiresAt } = req.body;

    // Si la permission n'existe pas encore, on la crée
    let permission = await prisma.permission.findUnique({
      where: { name: permissionName }
    });
    
    if (!permission) {
      permission = await prisma.permission.create({
        data: {
          name: permissionName,
          description: `Permission ${permissionName}`
        }
      });
    }
    
    // 2. Attribuer la permission à l'utilisateur
    // upsert() : créer si n'existe pas, mettre à jour si existe déjà
    const userPermission = await prisma.userPermission.upsert({
      where: {
        userId_permissionId: {
          userId: req.params.userId,
          permissionId: permission.id
        }

      create: {
        userId: req.params.userId,
        permissionId: permission.id,
        granted: true,                              // Accorder la permission
        expiresAt: expiresAt ? new Date(expiresAt) : null  // Expiration optionnelle
      },
      update: {
        granted: true,                              // Ré-accorder si révoquée
        expiresAt: expiresAt ? new Date(expiresAt) : null  // Mettre à jour l'expiration
      }
    });
    
    res.json({
      message: 'Permission granted',
      permission: userPermission
    });
  }
);

  • Flexibilité maximale : Permissions personnalisées par utilisateur sans créer de nouveaux rôles
  • Permissions temporaires : Expiration automatique des permissions (ex: accès temporaire pour un projet)

function authorize(...requiredPermissions) {
  return async (req, res, next) => {
    // Récupérer les permissions de l'utilisateur
    const userPermissions = await getUserPermissions(req.user.sub);
    
    // Vérifier si l'utilisateur a toutes les permissions requises
    const hasAllPermissions = requiredPermissions.every(perm =>
      userPermissions.includes(perm)
    );
    
    // Logger TOUTE tentative d'autorisation (succès ou échec)
    logger.info('Authorization check', {
      userId: req.user.sub,
      email: req.user.email,
      role: req.user.role,
      action: req.method,           // GET, POST, DELETE, etc.
      resource: req.path,           // /api/events/123
      required: requiredPermissions, // ['delete:events']
      userHas: userPermissions,     // Toutes les permissions de l'utilisateur
      granted: hasAllPermissions,   // true ou false
      ip: req.ip,                   // Adresse IP du client
      timestamp: new Date().toISOString()
    });
    
    if (!hasAllPermissions) {
      // Logger spécifiquement les refus d'accès (plus important pour la sécurité)
      logger.warn('Access denied', {
        userId: req.user.sub,
        email: req.user.email,
        action: req.method,
        resource: req.path,
        required: requiredPermissions,
        missing: requiredPermissions.filter(p => !userPermissions.includes(p))  // Permissions manquantes
      });
      
      return res.status(403).json({ error: 'Forbidden' });
    }
    
    next();
  };
}

3.1 Pourquoi HTTPS est obligatoire

HTTP (sans chiffrement) laisse toutes les données circuler en clair sur le réseau. Un attaquant présent sur le même Wi-Fi peut intercepter :

  • Mots de passe et identifiants sensibles
  • Tokens d'authentification et cookies de session
  • Données personnelles et formulaires
  • Contenu complet des requêtes et réponses

HTTPS ajoute TLS (Transport Layer Security) qui chiffre l'entièreté du trafic. Résultat : même si les paquets sont interceptés, ils sont illisibles sans la clé.

Statistiques clés

Année Part du web en HTTPS
2015 ≈ 40 %
2024 95 % et plus
⚠️ Chrome / Firefox / Edge

Les navigateurs modernes marquent désormais les sites HTTP comme « Non sécurisé ». Cela impacte la confiance utilisateur, le SEO et la conformité (RGPD, PCI-DSS).

✅ À retenir
  • HTTPS est un prérequis pour toute mise en production.
  • Il protège les données, améliore le référencement et évite les alertes de sécurité.
3.2 Comment fonctionne TLS (simplifié)

Les objectifs de TLS

  1. Confidentialité : personne ne lit les données échangées.
  2. Intégrité : toute modification est détectée.
  3. Authentification : le serveur prouve son identité.

Handshake TLS (simplifié)

Le handshake est la « Poignée de main » qui établit une connexion sécurisée avant d'échanger des données applicatives.

Client                                    Serveur
  │                                          │
  │ 1. ClientHello (versions, algorithmes)  │
  │─────────────────────────────────────────>│
  │                                          │
  │ 2. ServerHello + Certificat             │
  │<─────────────────────────────────────────│
  │                                          │
  │ 3. Vérification du certificat           │
  │    - CA de confiance ?                  │
  │    - Domaine correspondant ?            │
  │    - Pas expiré ?                       │
  │                                          │
  │ 4. Échange de clés (Diffie-Hellman)     │
  │<────────────────────────────────────────>│
  │    → Génère une clé de session          │
  │                                          │
  │ 5. Communication chiffrée (AES)         │
  │<────────────────────────────────────────>│
🔑 Rôle des clés
  • Le certificat contient la clé publique exposée au client.
  • La clé privée reste sur le serveur (ne jamais la diffuser).
  • Chaque connexion génère une clé de session symétrique unique.
  • TLS combine chiffrement asymétrique (échange de clé) et symétrique (données) pour optimiser sécurité + performance.
⚠️ Erreurs à éviter
  • Utiliser TLS < 1.2 : vulnérabilités connues.
  • Exposer la clé privée (stockage non chiffré, dépôt Git).
  • Renouveler le certificat trop tard : service indisponible ou alertes navigateur.
3.3 Les certificats SSL/TLS

Comprendre un certificat TLS

Un certificat est une carte d’identité numérique signée par une autorité de certification (CA). On y trouve :

  • Les noms de domaine couverts (ex. api.smartcity.fr).
  • La clé publique du serveur.
  • La signature de la CA qui atteste l’authenticité.
  • Les dates de validité (début / expiration).
Qui vérifie quoi ?

DV (Domain Validation) : la CA vérifie que vous contrôlez le domaine (challenge DNS/HTTP). Automatisable et gratuit.

OV (Organization Validation) : contrôle administratif de l’entreprise (documents légaux, appel téléphonique).

EV (Extended Validation) : audit poussé (existence juridique, adresse, dirigeants). Réservé aux banques/grandes organisations.

Dans tous les cas, c’est la CA qui mène les vérifications avant de signer votre certificat.

Types de validation

Type Validation Usage typique
DV Preuve de contrôle du domaine (DNS, HTTP challenge) APIs, sites web standards (Let's Encrypt)
OV Validation de l’organisation (documents juridiques) Sites corporate, B2B
EV Audit complet + vérifications physiques Banques, fintech, e-commerce critique
Let's Encrypt & co
  • Let's Encrypt : CA libre et gratuite. Certificats DV valables 90 jours, renouvellement automatique.
  • Services managés (Cloudflare, AWS ACM, GCP Certificate Manager) : génèrent et renouvellent les certificats pour vous.
  • Certificats locaux : en développement, utilisez mkcert pour créer un certificat de test sans alertes navigateur.
Glossaire express
  • CA (Certificate Authority) : tiers de confiance qui signe les certificats.
  • CSR (Certificate Signing Request) : fichier contenant votre clé publique et vos infos, envoyé à la CA.
  • Chaîne de confiance : certificat serveur + certificats intermédiaires + certificat racine.
  • Wildcard : certificat couvrant tous les sous-domaines d’un domaine (ex. *.smartcity.fr).
3.4 Obtenir un certificat

L’objectif n’est pas de réciter une configuration Nginx par cœur, mais de savoir où activer HTTPS et quels outils utiliser selon le contexte.

Scénarios courants
  • Plateformes cloud (Vercel, Netlify, Render, Heroku, Cloud Run) : HTTPS est activé automatiquement, certificats renouvelés par la plateforme.
  • Reverse proxy / load balancer (Traefik, Caddy, Nginx, AWS ALB, Cloudflare) : ces services terminent TLS et renouvellent souvent les certificats (Let's Encrypt intégré).
  • Kubernetes : un ingress controller (Traefik = reverse proxy orienté microservices, Nginx Ingress Controller, Istio) + cert-manager gèrent l’ensemble.
Quand générer soi-même ?
  • Auto-hébergement simple : certbot + Nginx/Apache pour obtenir un DV Let's Encrypt.
  • Environnement local : mkcert crée un certificat signé par votre machine (zéro alerte navigateur).
  • Besoins avancés : certificats wildcard ou multi-domaines via challenge DNS automatisé.

Dans tous les cas, automatisez le renouvellement (cron, GitHub Actions, chart Helm…).

Checklist HTTPS
  1. Terminer TLS via votre plateforme cloud ou, en auto-hébergement, via un reverse proxy.
  2. Rediriger systématiquement HTTP → HTTPS (code 301).
  3. Limiter les protocoles à TLS 1.2+ et utiliser une liste d’algorithmes recommandée (profil Mozilla “intermediate”).
  4. Ajouter les principaux headers de sécurité (cf. glossaire ci-dessous).
  5. Tester la configuration (SSL Labs, curl -I https://..., monitoring d’expiration).
Glossaire express
  • Reverse proxy : point d’entrée réseau qui reçoit les requêtes, termine TLS, applique des règles (headers, cache, load balancing) puis les transmet à votre application (ex : Nginx, Traefik, Caddy).
  • Traefik : reverse proxy open-source pensé pour les microservices et Kubernetes.
  • Caddy : serveur web qui gère automatiquement les certificats Let's Encrypt.
  • HSTS (Strict-Transport-Security) : indique au navigateur de n’utiliser que HTTPS pendant X temps.
  • X-Frame-Options : empêche le site d’être chargé dans une iframe (anti clickjacking).
  • Content-Security-Policy (CSP) : définit les sources autorisées pour scripts, CSS, images… (anti XSS).
  • Helmet.js : middleware Express qui configure ces headers automatiquement.
Focus TP SmartCity
  • En développement : utilisez mkcert + Helmet pour tester en HTTPS local.
  • En déploiement managé (Vercel, Netlify, Render, Cloud Run, etc.) : laissez la plateforme gérer HTTPS automatiquement.
  • En auto-hébergement : installez un reverse proxy (Traefik / Nginx) qui récupère automatiquement un certificat Let's Encrypt.
  • Le code Bash détaillé vu en cours est pour la culture : à vous de choisir la solution la plus simple dans votre environnement.
3.5 Attaques courantes et protections

1. Man-in-the-Middle (MITM)

Définition : Attaque où un attaquant intercepte et potentiellement modifie les communications entre deux parties sans qu'elles le sachent.

Protections :

  • ✅ HTTPS obligatoire
  • ✅ HSTS header
  • ✅ Certificate Pinning (technique mobile validant le certificat attendu) pour applications mobiles

2. Replay Attack

Définition : Attaque où une requête valide capturée est renvoyée au serveur pour reproduire une action (ex: un paiement).

Protection avec Nonce :

const usedNonces = new Set();

app.post('/api/transfer', (req, res) => {
  const { nonce, timestamp, ...data } = req.body;
  
  // Vérifier que le nonce (nombre aléatoire à usage unique) n'a jamais été utilisé
  if (usedNonces.has(nonce)) {
    return res.status(400).json({ error: 'Nonce already used' });
  }
  
  // Vérifier que la requête n'est pas trop vieille (5 min max)
  if (Date.now() - timestamp > 5 * 60 * 1000) {
    return res.status(400).json({ error: 'Request expired' });
  }
  
  usedNonces.add(nonce);
  setTimeout(() => usedNonces.delete(nonce), 10 * 60 * 1000);
  
  processTransfer(data);
  res.json({ success: true });
});

3. Token Theft

Définition : Vol de tokens d'authentification via XSS, sniffing (écoute du trafic réseau) ou malware (logiciel malveillant).

Stockage sécurisé côté client :

Méthode Vulnérabilité Recommandation
localStorage ❌ Accessible via JavaScript (XSS) Ne pas utiliser
sessionStorage ❌ Accessible via JavaScript (XSS) Ne pas utiliser
Cookie httpOnly ✅ Protégé contre XSS Recommandé

Configuration sécurisée :

res.cookie('access_token', token, {
  httpOnly: true,      // Pas accessible via JavaScript
  secure: true,        // HTTPS uniquement
  sameSite: 'strict',  // Protection CSRF (Cross-Site Request Forgery - exécution d'actions non autorisées)
  maxAge: 3600000      // 1 heure
});

4. Brute Force

Définition : Attaque par essais successifs de mots de passe jusqu'à trouver le bon.

Protection avec Rate Limiting :

Le rate limiting (limitation du nombre de requêtes par période) empêche les attaques automatisées.

const rateLimit = require('express-rate-limit');

// Rate limit global
const globalLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100
});
app.use('/api/', globalLimiter);

// Rate limit strict sur login
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5, // 5 tentatives max
  skipSuccessfulRequests: true
});
app.post('/api/auth/login', loginLimiter, loginHandler);

Blocage progressif :

const loginAttempts = new Map();

app.post('/api/auth/login', async (req, res) => {
  const attemptKey = `login:${req.body.email}:${req.ip}`;
  const attempts = loginAttempts.get(attemptKey) || { count: 0, lockedUntil: null };
  
  // Vérifier si bloqué
  if (attempts.lockedUntil && Date.now() < attempts.lockedUntil) {
    return res.status(429).json({ error: 'Account temporarily locked' });
  }
  
  // Validation credentials...
  const user = await validateCredentials(req.body);
  
  if (!user) {
    attempts.count++;
    
    // Blocage progressif
    if (attempts.count >= 10) {
      attempts.lockedUntil = Date.now() + 60 * 60 * 1000; // 1 heure
    } else if (attempts.count >= 5) {
      attempts.lockedUntil = Date.now() + 15 * 60 * 1000; // 15 min
    }
    
    loginAttempts.set(attemptKey, attempts);
    return res.status(401).json({ error: 'Invalid credentials' });
  }
  
  // Succès : réinitialiser
  loginAttempts.delete(attemptKey);
  res.json({ token: generateToken(user) });
});

Slow Hash avec bcrypt :

Le hashing (transformation irréversible d'un mot de passe) lent rend le brute force très coûteux.

const bcrypt = require('bcrypt');

// Création compte
const passwordHash = await bcrypt.hash(password, 12); // 2^12 itérations (~250ms)

// Login
const isValid = await bcrypt.compare(password, user.password_hash);

5. SQL Injection

Définition : Injection de code SQL malveillant dans une requête pour accéder, modifier ou supprimer des données non autorisées.

Protection :

// ❌ Vulnérable
const query = `SELECT * FROM users WHERE email = '${email}'`;

// ✅ Requêtes paramétrées
db.query('SELECT * FROM users WHERE email = ?', [email]);

// ✅ ORM (Object-Relational Mapping - outil qui gère automatiquement les requêtes)
const user = await prisma.user.findUnique({ where: { email } });

// ✅ Validation
const { body, validationResult } = require('express-validator');
app.post('/api/users',
  body('email').isEmail().normalizeEmail(),
  body('name').trim().escape(),
  handler
);

6. NoSQL Injection

Définition : Similaire à SQL injection mais pour les bases NoSQL (MongoDB, etc.), exploitant les opérateurs de requête.

Protection :

// ❌ Vulnérable
const email = req.body.email; // { "$ne": null }
db.collection('users').findOne({ email: email });

// ✅ Valider le type
if (typeof email !== 'string') {
  return res.status(400).json({ error: 'Invalid email format' });
}

// ✅ Sanitization (nettoyage des entrées)
const mongoSanitize = require('express-mongo-sanitize');
app.use(mongoSanitize());

7. Cross-Site Scripting (XSS)

Définition : Injection de scripts malveillants dans une page web, exécutés dans le navigateur des victimes.

Protection :

  • ✅ Sanitization des inputs utilisateur
  • ✅ Escaping (échappement des caractères spéciaux) des outputs
  • ✅ Content-Security-Policy header
  • ✅ Pas de innerHTML avec données utilisateur

8. Cross-Site Request Forgery (CSRF)

Définition : Attaque forçant un utilisateur authentifié à exécuter des actions non désirées sur une application web.

Protection :

  • ✅ Cookies avec sameSite: 'strict'
  • ✅ Tokens CSRF (jeton unique par session vérifiant l'origine de la requête)
  • ✅ Vérification du header Origin ou Referer

9. DDoS (Distributed Denial of Service)

Définition : Attaque visant à rendre un service indisponible en le submergeant de requêtes provenant de multiples sources.

Protection :

  • ✅ CDN (Content Delivery Network - réseau de serveurs distribuant le contenu) avec protection DDoS (Cloudflare)
  • ✅ Rate limiting
  • ✅ Load balancing (répartition de charge entre plusieurs serveurs)
  • ✅ WAF (Web Application Firewall - pare-feu applicatif filtrant le trafic HTTP)
3.6 Checklist sécurité complète

Cette checklist vous permet de vérifier que tous les aspects de sécurité sont couverts dans votre application.

  • ☐ Logs de toutes les décisions d'autorisation

Protection des données

  • ☐ Validation stricte de tous les inputs
  • ☐ Sanitization des données utilisateur

Secrets et configuration

3.8 Configuration complète sécurisée

Exemple d'implémentation Node.js/Express intégrant toutes les bonnes pratiques :

const express = require('express');
const helmet = require('helmet');
const rateLimit = require('express-rate-limit');
const mongoSanitize = require('express-mongo-sanitize');
const hpp = require('hpp'); // HTTP Parameter Pollution protection
const cors = require('cors');
const winston = require('winston');

const app = express();

// =============================================
// LOGGING
// =============================================

const logger = winston.createLogger({
  level: 'info',
  format: winston.format.json(),
  transports: [
    new winston.transports.File({ filename: 'error.log', level: 'error' }),
    new winston.transports.File({ filename: 'combined.log' })
  ]
});

// =============================================
// SECURITY MIDDLEWARES
// =============================================

// Trust proxy (derrière Nginx)
app.set('trust proxy', 1);

// Helmet : headers de sécurité
app.use(helmet());

// CORS strict
app.use(cors({
  origin: process.env.ALLOWED_ORIGINS?.split(',') || ['https://smartcity.local'],
  credentials: true
}));

// Body parsing avec limite de taille
app.use(express.json({ limit: '10kb' }));
app.use(express.urlencoded({ extended: true, limit: '10kb' }));

// Protection NoSQL injection
app.use(mongoSanitize());

// Protection HTTP Parameter Pollution
app.use(hpp());

// Rate limiting global
const globalLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 100,
  message: 'Too many requests from this IP'
});
app.use('/api/', globalLimiter);

// Rate limiting login
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 5,
  skipSuccessfulRequests: true
});

// =============================================
// ROUTES
// =============================================

app.post('/api/auth/login', loginLimiter, loginHandler);
app.get('/api/events', authenticateJWT, authorize('read:events'), getEvents);

// =============================================
// ERROR HANDLING
// =============================================

// 404
app.use((req, res) => {
  res.status(404).json({ error: 'Not found' });
});

// Error handler
app.use((err, req, res, next) => {
  logger.error('Error', { error: err.message, path: req.path });
  res.status(500).json({ error: 'Internal server error' });
});

// =============================================
// START SERVER
// =============================================

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  logger.info(`Server started on port ${PORT}`);
});

// Graceful shutdown
process.on('SIGTERM', () => {
  logger.info('SIGTERM received, shutting down gracefully');
  server.close(() => process.exit(0));
});
✅ Ce que cette configuration apporte
  • Logging : Toutes les erreurs et événements sont enregistrés
  • Headers de sécurité : Helmet configure automatiquement tous les headers essentiels
  • CORS strict : Seules les origines autorisées peuvent accéder à l'API
  • Protection injections : NoSQL injection et HTTP Parameter Pollution bloqués
  • Rate limiting : Protection globale + protection renforcée sur login
  • Gestion d'erreurs : Erreurs capturées et loggées sans exposer de détails sensibles
  • Graceful shutdown : Arrêt propre du serveur lors des déploiements

📌 Points clés à retenir
  1. HTTPS est la fondation : Sans TLS, toutes les autres mesures de sécurité sont inutiles. C'est le premier rempart contre l'interception des données.
  2. La sécurité est une défense en profondeur : Aucune mesure seule ne suffit. Il faut combiner : HTTPS + Headers + Authentification + Autorisation + Rate Limiting + Monitoring + Validation.
  3. Les headers de sécurité sont essentiels : HSTS, CSP, X-Content-Type-Options protègent contre de nombreuses attaques côté client. Helmet.js les configure automatiquement.
  4. Rate limiting partout : Protection indispensable contre brute force et DoS. Appliquez-le globalement ET spécifiquement sur les endpoints sensibles.
  5. Logs et monitoring en continu : Logger toutes les tentatives d'accès, surtout les échecs. Les patterns suspects doivent déclencher des alertes automatiques.
  6. Les secrets hors du code : Variables d'environnement, rotation régulière, gestion centralisée avec Vault pour la production.
  7. Tests de sécurité réguliers : npm audit, Snyk, OWASP ZAP dans la CI/CD. La sécurité n'est pas un état mais un processus continu.
  8. Principe du moindre privilège : S'applique aux utilisateurs ET aux systèmes. Limitez l'accès au strict nécessaire.

⚠️ Erreurs courantes à éviter
  1. "Ma petite API n'intéresse personne"
    ❌ Faux. Les bots scannent TOUT internet. Même une API de test peut être compromise et utilisée pour des attaques.
  2. "J'ajouterai la sécurité plus tard"
    ❌ La sécurité doit être intégrée dès le début. La corriger après coup coûte 10x plus cher.
  3. "HTTPS suffit"
    ❌ HTTPS protège le transport, pas l'application. Il faut authentification, autorisation, validation, etc.
  4. "Je stocke les JWT dans localStorage"
    ❌ Vulnérable à XSS. Utilisez des cookies httpOnly.
  5. "Mes secrets sont dans .env donc c'est sûr"
    ❌ Si .env est dans Git, vos secrets sont publics. Utilisez .gitignore et un vault en production.
  6. "Je n'ai pas besoin de logs"
    ❌ Sans logs, impossible de détecter une attaque ou de faire un audit. Logger tout (sauf les données sensibles).
  7. "Rate limiting = mauvaise UX"
    ❌ Les vrais utilisateurs ne font pas 100 requêtes/seconde. Le rate limiting protège sans gêner.
  8. "Je teste la sécurité manuellement"
    ❌ Automatisez dans la CI/CD : npm audit, tests de sécurité, scan de secrets.
🎯 Scénario d'attaque réel : Chaîne d'exploitation

Voici comment une API mal sécurisée peut être compromise :

1. Reconnaissance
   ↓
   Attaquant scanne api.smartcity.local
   Découvre : pas de rate limiting, HTTP accepté

2. Exploitation initiale
   ↓
   Brute force sur /login (pas de limite)
   Trouve password faible : admin/password123

3. Élévation de privilèges
   ↓
   Token JWT dans localStorage (vulnérable XSS)
   Injection XSS via un champ non validé
   Vol du token admin

4. Mouvement latéral
   ↓
   Avec token admin, accès à /admin/users
   Pas de vérification ownership
   Modifie son propre compte en super-admin

5. Exfiltration de données
   ↓
   Dump de toute la base utilisateurs
   Pas de logs configurés = non détecté
   Pas de rate limiting = extraction rapide

6. Persistance
   ↓
   Crée un compte backdoor
   Modifie le code pour injecter une porte dérobée
   Pas de monitoring = reste actif des mois

Avec les bonnes pratiques

  • HTTPS obligatoire → Pas d'interception du trafic
  • Rate limiting → Brute force impossible
  • Passwords hashés (bcrypt) → Même volés, inutilisables
  • JWT en cookies httpOnly → Pas de vol via XSS
  • Validation inputs → Pas d'injection XSS
  • Autorisation stricte → Pas d'élévation de privilèges
  • Logs centralisés → Détection rapide
  • Monitoring → Alertes automatiques
💭 Philosophie de la sécurité
  • Assume Breach (assumer la compromission) : Ne partez pas du principe que votre système est inviolable. Demandez-vous plutôt : "Quand (pas si) je suis compromis, comment limiter les dégâts ?"
  • Zero Trust (confiance zéro) : Ne faites confiance à personne et rien par défaut. Vérifiez TOUT à CHAQUE requête.
  • Defense in Depth (défense en profondeur) : Plusieurs couches de sécurité. Si une échoue, les autres protègent encore.
  • Principle of Least Privilege (moindre privilège) : Donnez uniquement les accès nécessaires, rien de plus.
  • Fail Secure (échec sécurisé) : En cas d'erreur, refusez l'accès plutôt que de l'autoriser par défaut.
  • Keep It Simple (simplicité) : Plus c'est complexe, plus il y a de bugs et de failles. Privilégiez la simplicité.

  • DPO (Data Protection Officer) si nécessaire : désigner un référent RGPD dans les organisations soumises à l’obligation.
📊 Synthèse finale : Les 3 piliers de la sécurité API

1️⃣ AUTHENTIFICATION

"Qui êtes-vous ?"

  • Basic Auth : Prototypage uniquement
  • API Keys : Services B2B
  • JWT : Standard moderne
  • OAuth 2.0 : APIs publiques

2️⃣ AUTORISATION

"Que pouvez-vous faire ?"

  • RBAC : Permissions par rôle
  • ABAC : Permissions par attributs
  • Scopes : Permissions granulaires OAuth

3️⃣ PROTECTION DU TRANSPORT

"Comment protéger les échanges ?"

  • HTTPS/TLS : Chiffrement obligatoire
  • Headers : CSP, HSTS, etc.
  • Rate Limiting : Anti brute-force/DoS
  • Monitoring : Détection d'anomalies
