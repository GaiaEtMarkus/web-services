PARTIE 1 : ARCHITECTURE MICROSERVICES

Du monolithe aux microservices – motivations, limites, architecture cible.

Partie 1 : Architecture microservices (50 min)

5 sous-parties
1.1 Du monolithe aux microservices

Les SI sont longtemps restés monolithiques : mainframes, applications client-serveur, puis gros WAR/EAR Java ou applis .NET uniques. Cette approche a évolué vers des monolithes modulaires ou des architectures orientées services (SOA) avec ESB, avant que les microservices ne popularisent la découpe fine et le déploiement indépendant. Aujourd'hui, on combine souvent plusieurs styles (monolithe + microservices, micro-frontends, évènementiel) selon la maturité et la taille du projet. Les microservices ne sont pas réservés aux « Big Tech » :

🌍 Qui utilise les microservices ? Pourquoi ?

Big Tech & plateformes mondiales (Netflix, Amazon, Uber, Airbnb, Spotify, Doctolib, Back Market…)

  • Trafic massif → scalabilité par domaine (ex : seulement “streaming” ou “paiement”).
  • Équipes nombreuses → organisation par domaines indépendants.
  • Déploiements continus → chaque service évolue sans couper les autres.

Scale-up / SaaS en forte croissance (marketplaces, plateformes de réservation, outils B2B…)

  • Besoin de livrer très vite de nouvelles fonctionnalités.
  • Équipes qui grossissent → architecture modulaire indispensable.
  • Domaines métier multiples (facturation, utilisateurs, notifications…) → découpe naturelle.

Secteurs riches en domaines métier (Banque, Assurance, Transport, Télécom, e-commerce…)

  • Domaines très différenciés (sinistres, contrats, clients, logistique…).
  • Approche Domain-Driven Design facilitée (un microservice = un sous-domaine).
🔍 Le monolithe : simple mais limité

Monolithe = un seul projet, un seul déploiement, un seul serveur.

✅ Avantages
  • Développement simple : un repo, une stack
  • Déploiement rapide : npm start
  • Tests d'intégration faciles
  • Excellentes performances (pas d'appels réseau)
  • Parfait pour MVP / petites équipes (<10)
❌ Limites à l'échelle
  • Scalabilité « tout ou rien »
  • Déploiements risqués (un bug = tout plante)
  • Équipes bloquées sur le même code
  • Technologie figée, build lent
📺 Retour d'expérience : Netflix
  • 2008 : Monolithe Java « ok »
  • 2009 : Corruption DB → 3 jours down → pertes majeures
  • 2010-2012 : Migration microservices
  • 2025 : 2000+ microservices, 4000 déploiements/jour

Leçon : multiplier les services permet d'isoler les pannes (si Recommendations tombe, Streaming continue).

🧱 Qu'est-ce qu'un microservice ?

Un service petit, autonome, fortement encapsulé.

  • Single responsibility (Events, Users, Payments...)
  • Base de données privée
  • API explicite (REST, gRPC, messages)
  • Déploiement indépendant
  • Équipe autonome (Two Pizza Team)

1.3 Quand (ne pas) utiliser les microservices ?
✅ Adoptez les microservices si :
  • Équipe > 15 personnes, besoin d'autonomie
  • Domaines métier multiples (Events, Users, Billing...)
  • Charges différentes (Events 1000 req/s vs Users 10 req/s)
  • Déploiements fréquents (CI/CD avancé)
  • Innovation technologique (Go, Rust...)
  • Haute disponibilité (isolation des pannes critique)
❌ Restez monolithe si :
  • Startup/MVP : vitesse > architecture
  • Petite équipe (<10) ou budget limité
  • Domaine simple (peu de fonctionnalités)
  • Pas d'expertise DevOps (K8s, observabilité)
💬 Martin Fowler
« Don't start with microservices. Start with a monolith and split when the pain is real. »

Signaux de migration :

  • Déploiement > 30 min
  • Équipes qui se marchent dessus
  • Scalabilité fine impossible
  • Base de données saturée
1.4 Les défis des microservices
1. Complexité opérationnelle

50 services = 50 repos, déploiements, bases, pipelines.

Solutions :

  • Kubernetes (orchestration)
  • Docker (conteneurs)
  • CI/CD (GitHub Actions, GitLab CI, Jenkins)
  • Infra as Code (Terraform, Ansible)

On passe d’un déploiement unique à une plateforme complète (registry, observabilité, pipelines). Sans automatisation, la dette explose.

2. Communication inter-services

Latence réseau cumulée (A → B → C).

Solutions :

  • Caching (Redis)
  • Messaging asynchrone (RabbitMQ, Kafka)
  • API Gateway (routage unique)

Chaque appel devient un appel réseau : il faut compenser avec du cache, de l’asynchrone et un point d’entrée cohérent.

RabbitMQ est un broker AMQP : chaque message est placé dans une file et consommé par un seul service (garantie de livraison, ack/nack, retries). Kafka est une plateforme d’event streaming : les événements sont stockés dans un log distribué, plusieurs consumers peuvent lire le même flux, et on peut rejouer l’historique pour de l’analytics ou de l’event sourcing.

3. Données distribuées

Pas de transactions ACID multi-services : chaque service possède sa base, la cohérence se fait à terme.

  • Saga Pattern : enchaîner des transactions locales puis déclencher des actions de compensation si une étape échoue.
  • Eventual Consistency : accepter que les données convergent après coup (notifications, recalcul, délais de propagation).
  • Event Sourcing : stocker les événements plutôt que l’état final, pour reconstruire ou rejouer l’historique.

Saga = workflow fiable sans transaction globale : on découpe “Commander un produit” en mini transactions (commande, paiement, stock…). Si “stock” échoue, on déclenche les compensations (rembourser, annuler la commande) pour revenir à un état cohérent.

Eventual consistency = les services ne sont pas synchro instantanément (ex : Stock reçoit l’événement 50 ms après Commande, Notification 200 ms plus tard) mais ils convergent. On accepte ce délai pour bénéficier d’échanges asynchrones (Kafka, RabbitMQ) et d’une meilleure scalabilité.

Event sourcing = on garde tous les événements (“+200€”, “-50€”, “+300€”) plutôt que l’état final (“solde = 450€”). L’état est la somme des événements. Idéal pour l’audit, la réparation par replay, et les architectures CQRS/bancaires.

Chaque service possède sa base : on raisonne donc en cohérence à terme et en transactions orchestrées plutôt qu’en commit global.

4. Monitoring & debugging

Une requête traverse 5 services : où se situe l'erreur ?

  • Distributed Tracing (Jaeger, Zipkin)
  • Centralized Logging (ELK)
  • Correlation ID (propagation d'un identifiant unique)

Les logs locaux ne suffisent plus : il faut corréler les requêtes d’un bout à l’autre (traces distribuées), centraliser les logs pour les requêter (ELK), et propager un identifiant unique (Correlation ID) pour suivre tout le parcours d’une requête.

🆔 Exemple de Correlation ID
// API Gateway génère un ID unique
const correlationId = uuidv4();
req.headers['x-correlation-id'] = correlationId;

// Chaque service logge avec cet ID
logger.info(`[${req.headers['x-correlation-id']}] Processing event`);

// Dans les logs :
// [abc-123] Gateway: Received request
// [abc-123] Events Service: Fetching event
// [abc-123] Payment Service: Processing payment
// [abc-123] Notification Service: Sending email

PARTIE 2 : API GATEWAY

Point d'entrée unique : sécurité, routage, agrégation et performances.

Partie 2 : API Gateway (45 min)

4 sous-parties
2.1 Qu'est-ce qu'une API Gateway ?

Une API Gateway est le point d’entrée officiel de tous les clients (web, mobile, partenaires) vers votre système. Contrairement à un simple reverse proxy, elle comprend les notions métier (ex : “/api/events” → Events Service) et applique une politique uniforme : authentification, rate limiting, observabilité, transformation des payloads. Elle permet également de masquer la topologie interne (routage, protocoles, versions) et de présenter une API cohérente même quand les microservices évoluent indépendamment.

Sans Gateway, chaque client devrait connaître toutes les URLs internes, gérer CORS, répéter l’authentification et supporter les changements d’infrastructure. Avec une Gateway, on centralise la sécurité, la traduction des formats, l’agrégation de données et l’accès aux services privés. C’est aussi un point stratégique pour déployer des fonctionnalités transverses (observabilité, A/B testing, mise en cache, failover).

💡 Définition

Reverse proxy intelligent et sécurisé qui centralise l'accès aux microservices.

Analogie : la réception d'un hôtel : on passe toujours par elle avant d’accéder aux chambres.

❌ Sans Gateway (chaos)
Client → http://events-service:3001/events
        ↳ http://users-service:3002/users
        ↳ http://payments-service:3003/payments
  
  • Couplage fort (le client connaît tout)
  • Authentification/CORS répétés
  • Impossible de cacher les URLs internes
✅ Avec Gateway (propre)
Client → https://api.smartcity.fr (Gateway)
                       ↳ Events / Users / Payments (routage interne)
  
  • Une seule URL publique
  • Authentification centralisée
  • Observabilité et politiques globales
2.2 Responsabilités clés
1. Routage

Rediriger chaque endpoint vers le service cible.

const routes = {
    '/api/events': 'http://events:3001',
    '/api/users' : 'http://users:3002'
  };
  
  proxy(req, res, routes[match(req.path)]);
2. Authentification

Vérifier le JWT une seule fois puis propager l'identité.

const token = req.headers.authorization?.split(' ')[1];
  const decoded = jwt.verify(token, SECRET);
  req.headers['x-user-id'] = decoded.sub;
3. Rate limiting

Limiter les abus (DDOS, bots).

app.use('/api/', rateLimit({
    windowMs: 15 * 60 * 1000,
    max: 100
  }));
4. Load balancing

Répartir la charge sur plusieurs instances.

const instances = ['events-1','events-2'];
  const target = roundRobin(instances);
  proxy(req, res, target);
5. Agrégation

Composer un dashboard en un appel.

const [events, user] = await Promise.all([...]);
  res.json({ events, user });
6. Cache & transformation

Réduire la charge des services.

const cached = await redis.get('events:all');
  if (cached) return res.json(JSON.parse(cached));
2.3 Implémentation Node.js (Express)

Base pour une Gateway SmartCity (dev/test) :

const express = require('express');
  const { createProxyMiddleware } = require('http-proxy-middleware');
  const jwt = require('jsonwebtoken');
  const rateLimit = require('express-rate-limit');
  
  const services = {
    events: process.env.EVENTS_URL || 'http://localhost:3001',
    users: process.env.USERS_URL || 'http://localhost:3002',
    payments: process.env.PAYMENTS_URL || 'http://localhost:3003'
  };
  
  function authenticate(req, res, next) {
    const token = req.headers.authorization?.split(' ')[1];
    if (!token) return res.status(401).json({ error: 'No token' });
    try {
      const decoded = jwt.verify(token, process.env.JWT_SECRET);
      req.headers['x-user-id'] = decoded.sub;
      req.headers['x-user-role'] = decoded.role;
      next();
    } catch {
      res.status(401).json({ error: 'Invalid token' });
    }
  }
  
  const app = express();
  app.use(rateLimit({ windowMs: 15 * 60 * 1000, max: 100 }));
  
  app.use('/api/events', authenticate, createProxyMiddleware({
    target: services.events,
    changeOrigin: true,
    pathRewrite: { '^/api/events': '' }
  }));
  // ... idem pour users / payments
  
  app.listen(process.env.PORT || 8080);

Health-check : exposez /health (statut, versions, dépendances) pour l'observabilité et le Service Discovery.

PARTIE 3 : SERVICE DISCOVERY

Comment localiser dynamiquement les services dans une architecture distribuée.

Partie 3 : Service Discovery (30 min)

4 sous-parties
3.1 Pourquoi le Service Discovery ?

Problème : avec des services qui scalent automatiquement (nouvelles instances, IPs dynamiques), comment l’API Gateway ou les autres services savent où envoyer les requêtes ? Impossible de maintenir un fichier de configuration manuel si les IPs changent toutes les minutes.

Service Discovery = un annuaire dynamique. Chaque service s’y enregistre au démarrage avec son nom (“events”), son adresse (IP + port) et des métadonnées. Les autres services interrogent cet annuaire pour savoir où contacter “events”. Si une instance tombe, l’annuaire la retire automatiquement. C’est le “DNS (Domain Name System)” intelligent des microservices.

❌ Configuration statique
const services = {
  events: 'http://192.168.1.10:3001'
}; // Et si cette instance tombe ?
  • Maintenance manuelle (erreurs, oublis)
    • li>Impossible de supporter le scaling horizontal
  • Downtime dès qu’une IP change
✅ Service Discovery dynamique
const eventsInstances = registry.getInstances('events');
// → ['192.168.1.10:3001','192.168.1.11:3001']
  • Enregistrement et retrait automatiques
  • Health-checks pour ne router que vers les instances saines
  • Support du scaling et des déploiements rolling
  • Clients et services n’ont plus besoin de connaître les IPs/ports en dur
  • Peut exposer l’info via API REST, DNS, ou drivers dédiés
🧱 Architecture type
1. Service Events démarre → s'enregistre ("events", 10.0.1.5:3001)
2. Le registre (Consul, Eureka, K8s) vérifie periodiquement /health
3. La Gateway demande : "Donne-moi une instance de events"
4. Le registre renvoie la liste healthy
5. La Gateway choisit une instance (round-robin) et route l'appel
6. Si l'instance ne répond plus, elle est retirée automatiquement

Le même mécanisme permet aussi aux services de se contacter entre eux (Service A interroge le registre pour trouver Service B).

3.2 Comment ça fonctionne ?
🔁 Cycle d’enregistrement / découverte
  1. Le service démarre → s’enregistre dans le registre (nom, IP, port, tags)
  2. Le registre exécute des health-checks (/health) pour vérifier la disponibilité
  3. Les clients (gateway, autres services) interrogent le registre pour obtenir les instances valides
  4. En cas de panne, le registre retire l’instance et renvoie uniquement les nœuds healthy
3.3 Solutions : Consul & Kubernetes
Consul (HashiCorp)

Registre distribué + DNS + KV store. Consul s’installe comme un cluster de serveurs auquel chaque service s’enregistre via un agent local ou une API HTTP. Il expose l’inventaire des services via HTTP, DNS ou un client officiel. On peut y stocker des métadonnées (tags, version, datacenter) et définir des health-checks très fins.

const consul = require('consul')({ host: 'consul', port: 8500 });

async function register() {
  await consul.agent.service.register({
    id: 'events-1',
    name: 'events',
    address: '192.168.1.10',
    port: 3001,
    check: {
      http: 'http://192.168.1.10:3001/health',
      interval: '10s',
      timeout: '5s'
    }
  });
}

Gateway → consul.health.service('events') → liste des instances healthy. Consul maintient aussi un KV store et peut déclencher des événements (watch) lorsqu’une instance change d’état.

Kubernetes (Service Discovery natif)

Chaque “Service” K8s possède un DNS interne (`http://events-service`). Le DNS est mis à jour automatiquement quand les pods scalent ou se redéploient. Les probes (liveness/readiness) déterminent si un pod est routable.

apiVersion: v1
kind: Service
metadata:
  name: events-service
spec:
  selector:
    app: events
  ports:
    - port: 80
      targetPort: 3001
// Gateway
fetch('http://events-service/events'); // Kubernetes résout

K8s se charge du load balancing et du health-check via les probes. Pour un déploiement Cloud-native, on n’a donc pas besoin d’outil externe (Consul/Eureka).

3.4 Health checks & résilience

Chaque service expose un endpoint simple qui vérifie ses dépendances (DB, cache, file). Le registre ou l’orchestrateur l’appelle régulièrement pour savoir si l’instance est “healthy”. On peut distinguer :

  • Liveness : est-ce que le processus tourne encore ?
  • Readiness : est-ce que le service est prêt à accepter des requêtes (DB connectée, cache warm) ?
  • Startup (K8s) : délai avant que le service soit considéré alive.
app.get('/health', async (req, res) => {
  try {
    await db.query('SELECT 1');
    res.status(200).json({
      status: 'healthy',
      service: 'events-service',
      timestamp: new Date().toISOString()
    });
  } catch (error) {
    res.status(503).json({
      status: 'unhealthy',
      error: error.message
    });
  }
});

Consul / Eureka : si plusieurs checks échouent, le service est marqué unhealthy. La Gateway et les autres services ne l’utilisent plus jusqu’à ce qu’il redevienne sain.

Kubernetes : les probes liveness/readiness sont natives. Si un pod échoue, K8s le redémarre ou cesse d’y router le trafic.

PARTIE 4 : PATTERNS ESSENTIELS

Résilience et transactions distribuées dans une architecture microservices.

Partie 4 : Patterns essentiels (50 min)

4 sous-parties
4.1 Circuit Breaker
❌ Problème (effet domino)

Service A appelle Service B (timeout 5s). Si B est down :

  • 100 requêtes/s × 5s = 500 threads bloqués
  • A finit par tomber (cascade)
✅ Solution : Circuit Breaker

Disjoncteur logiciel : coupe les appels après N échecs, fail fast, retente plus tard.

Les 3 états
CLOSED → fonctionnement normal
   ↓ (N échecs)
OPEN  → toutes les requêtes échouent instantanément
   ↓ (délai, ex : 60s)
HALF-OPEN → on teste 1 requête
   → succès → CLOSED
   → échec  → OPEN
class CircuitBreaker {
  constructor(threshold = 5, timeout = 60000) {
    this.state = 'CLOSED';
    this.failureCount = 0;
    this.threshold = threshold;
    this.timeout = timeout;
    this.nextAttempt = Date.now();
  }
  async call(fn) {
    if (this.state === 'OPEN') {
      if (Date.now() < this.nextAttempt) {
        throw new Error('Circuit breaker OPEN');
      }
      this.state = 'HALF-OPEN';
    }
    try {
      const result = await fn();
      this.success();
      return result;
    } catch (error) {
      this.failure();
      throw error;
    }
  }
  success() {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }
  failure() {
    this.failureCount++;
    if (this.failureCount >= this.threshold) {
      this.state = 'OPEN';
      this.nextAttempt = Date.now() + this.timeout;
    }
  }
}

Libraries : Node.js – opossum, Java – Resilience4j, Python – pybreaker.

4.2 Saga Pattern
Problème : pas de transaction ACID cross-services

ACID = Atomicité, Cohérence, Isolation, Durabilité. Ces garanties sont assurées par un moteur de base de données unique. Dans une architecture microservices, chaque service a sa DB : il est donc impossible d’avoir un commit global atomique couvrant Order + Payment + Reservation. Il faut orchestrer des transactions locales et, en cas d’échec, déclencher des opérations de compensation.

Créer une commande = Order + Payment + Reservation + Notification. Comment garantir la cohérence ?

Approche 1 : Chorégraphie (event-driven)
Order Service  → publie "OrderCreated"
Payment Service → écoute, tente le débit
   ↳ succès : publie "PaymentProcessed"
   ↳ échec  : publie "PaymentFailed"
Event Service → écoute "PaymentProcessed"
   ↳ succès : publie "SeatReserved"
   ↳ échec  : publie "ReservationFailed" (→ refund)
Notification Service → écoute "SeatReserved"

✅ Décentralisé, scalable — ❌ difficile à tracer/debugger.

Approche 2 : Orchestration
class OrderSaga {
  async execute(payload) {
    let orderId, paymentId;
    try {
      const order = await http.post('order-service/orders', payload);
      orderId = order.id;

      const payment = await http.post('payment-service/payments', { orderId, amount: payload.amount });
      paymentId = payment.id;

      await http.post('event-service/reservations', { orderId, eventId: payload.eventId });
      await http.post('notification-service/send', { userId: payload.userId, type: 'order_confirmation' });
      return { success: true, orderId, paymentId };
    } catch (error) {
      await compensate({ orderId, paymentId });
      return { success: false, error: error.message };
    }
  }
}

4.3 Event-Driven Architecture
❌ Synchrone
Client → Gateway → Order Service (attend 2s)
                     → Payment Service (attend 1s)
                     → Notification Service (attend 3s)
= 6s de latence, tout échoue si Notification down
✅ Asynchrone (events)
Client → Gateway → Order Service (réponse 200ms)
Order Service publie "OrderCreated" dans RabbitMQ
Payment / Notification / Analytics consomment en parallèle
Message queue vs Event stream
  • RabbitMQ / SQS : message → 1 consumer, supprimé après consommation.
  • Kafka / Kinesis : événement → plusieurs consumers, log persistant (replay possible).
// Publisher (Order Service)
const exchange = 'events';
channel.publish(exchange, '', Buffer.from(JSON.stringify({
  type: 'OrderCreated',
  data: { orderId: order.id, userId: order.userId }
})));

// Consumer (Payment)
channel.consume('payment-queue', async (msg) => {
  const event = JSON.parse(msg.content.toString());
  if (event.type === 'OrderCreated') {
    try {
      await processPayment(event.data);
      channel.ack(msg);
    } catch (error) {
      channel.nack(msg, false, true); // retry
    }
  }
});

Avantages : découplage total, résilience (si un consumer est down, les autres continuent), scalabilité horizontale, performance.

4.4 Autres patterns de résilience
Timeout

Ne jamais attendre indéfiniment.

async function callWithTimeout(url, timeout = 5000) {
  const controller = new AbortController();
  const id = setTimeout(() => controller.abort(), timeout);
  try {
    const response = await fetch(url, { signal: controller.signal });
    clearTimeout(id);
    return response;
  } catch (error) {
    if (error.name === 'AbortError') throw new Error('Request timeout');
    throw error;
  }
}
Retry + Backoff
async function retry(fn, maxRetries = 3) {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (attempt === maxRetries) throw error;
      const delay = Math.pow(2, attempt) * 1000; // 2s, 4s, 8s
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }
}
Bulkhead

Isoler les ressources pour éviter qu’un service saturé consomme toutes les connexions.

const pLimit = require('p-limit');
const paymentLimit = pLimit(10); // max 10 requêtes simultanées

app.post('/api/orders', async (req, res) => {
  try {
    const payment = await paymentLimit(() => fetch('http://payment-service:3003/process'));
    res.json({ success: true });
  } catch (error) {
    res.status(500).json({ error: error.message });
  }
});
