Projet Fil Rouge — SmartCity

Mise en pratique des Web Services

Objectifs, consignes, livrables, barème et jalons pour réussir la soutenance.

Retour à l'accueil

Backend du Frontend (BFF) — requis

Le frontend doit s’appuyer sur un petit backend dédié pour la sécurité et l’orchestration.

  • Proxy des appels vers les 4 APIs (le navigateur n’envoie jamais les API Keys directement).
  • Stockage et injection des API Keys côté serveur (secrets hors du navigateur).
  • Gestion de l’auth utilisateurs (JWT/OAuth 2.0), sessions si nécessaire.
  • Centralisation: CORS, rate limiting, logs, gestion des erreurs.
  • Agrégation d’appels (un endpoint pour plusieurs services côté front).

Bénéfices: sécurité, contrôle, simplification du client et meilleure observabilité.

📘 Informations générales

Formation : Mastère 2 - Web Services

Durée totale : 9 jours

Évaluation finale : Jour 9

Note : /40 points

Modalité : Projets en groupe de 3-4 personnes

🎯 Objectifs pédagogiques

Ce projet fil rouge a pour objectif de vous faire mettre en pratique les principaux concepts vus en cours sur les Web Services, dans un contexte professionnel réaliste.

Vous devrez démontrer votre maîtrise de :

  • Conception et développement d'APIs REST
  • Sécurité des Web Services (authentification, autorisation, API Keys)
  • Documentation technique (OpenAPI/Swagger)
  • Choix architecturaux justifiés
  • Bonnes pratiques professionnelles

📋 Description du projet

Contexte

Dans le cadre d'un écosystème SmartCity, plusieurs services indépendants doivent coexister et être accessibles via une application frontend centralisée.

La formation est divisée en 5 groupes :

🔧 4 Groupes Backend (4 personnes/groupe)

Chaque groupe développe un Web Service REST sur un thème SmartCity :

  • Groupe 1 : Service de diététique et nutrition
  • Groupe 2 : Service de diététique et nutrition (approche différente)
  • Groupe 3 : Service de gestion de parking et stationnement
  • Groupe 4 : Service d'alertes citoyennes

🎨 1 Groupe Frontend (3 personnes)

Développe une application frontend qui consomme les 4 APIs backend et gère l'authentification des utilisateurs finaux.

🔐 Architecture de sécurité

Pour les groupes Backend

Authentification B2B (Backend ↔ Frontend) :

  • Utilisation d'API Keys pour authentifier le frontend (client de l'API)
  • Chaque groupe backend génère et fournit une API Key au groupe frontend
  • Les requêtes du frontend vers les backends doivent inclure cette API Key

Pourquoi des API Keys ?

C'est la pratique standard professionnelle pour les intégrations entre services (ex: Stripe, SendGrid, Google Maps API, etc.). Lorsqu'une application souscrit à une API tierce, elle reçoit une clé unique qui l'identifie.

Pour le groupe Frontend

Double authentification à implémenter :

1. Authentification des utilisateurs finaux (B2C) :

  • Implémentation de JWT (JSON Web Tokens)
  • Implémentation d'OAuth 2.0 (Google, GitHub, etc.)
  • L'utilisateur doit pouvoir choisir sa méthode d'authentification

2. Authentification vers les backends (B2B) :

  • Utilisation des API Keys fournies par chaque groupe backend
  • Envoi de l'API Key dans les headers des requêtes vers les backends

Schéma d'authentification Frontend :

Utilisateur Final
    │
    ├─ Option 1 : Login/Password → JWT généré par le Frontend
    └─ Option 2 : OAuth 2.0 (Google, GitHub...) → Token OAuth
    
    ↓ (utilisateur authentifié)
    
Frontend (possède le JWT ou OAuth Token)
    │
    └─ Appels vers les 4 backends avec API Key dans les headers
        
        Backend 1 → Vérifie API Key → Répond
        Backend 2 → Vérifie API Key → Répond
        Backend 3 → Vérifie API Key → Répond
        Backend 4 → Vérifie API Key → Répond

📊 Barème d'évaluation (Total : /40)

1. Code et Implémentation (/10 points)

Pour les groupes Backend :

  • Qualité du code (2 pts) : Code propre, structuré, lisible, nommage cohérent, pas de duplication, commentaires pertinents
  • Architecture (2 pts) : Séparation des responsabilités, structure logique, modularité
  • Fonctionnalités (3 pts) : API fonctionnelle, gestion des API Keys, CRUD complet, valeur ajoutée
  • Base de données (2 pts) : Schéma cohérent, relations bien définies, migrations/seeds (bonus)
  • Gestion des erreurs (1 pt) : Try/catch appropriés, messages clairs, codes HTTP corrects

Pour le groupe Frontend :

  • Qualité du code (2 pts) : Code propre, composants réutilisables, gestion de l'état
  • Architecture (2 pts) : Structure logique, séparation des concerns
  • Fonctionnalités (3 pts) : Authentification JWT/OAuth fonctionnelle, intégration avec 4 backends, choix utilisateur
  • Base de données / Gestion utilisateurs (2 pts) : Stockage utilisateurs, gestion tokens, sécurité
  • Gestion des erreurs (1 pt) : Erreurs réseau, feedback utilisateur, fallbacks

2. Documentation et Contrat API (/10 points)

Pour les groupes Backend :

  • README.md (2 pts) : Complet, instructions fonctionnelles, exemples
  • Contrat API OpenAPI/Swagger (4 pts) : Routes documentées, schémas, exemples, accessible via /api-docs
  • Collection Postman (1 pt) : Routes testables, variables configurées
  • Documentation des API Keys (2 pts) : Comment obtenir/utiliser, format, exemples
  • Git (1 pt) : Historique cohérent, messages clairs, .gitignore approprié

Pour le groupe Frontend :

  • README.md (3 pts) : Complet, setup, documentation authentification
  • Documentation de l'authentification (4 pts) : Diagrammes JWT/OAuth, schéma BDD, gestion tokens
  • Documentation des intégrations (2 pts) : Consommation des 4 APIs, gestion API Keys, stratégies erreurs
  • Git (1 pt) : Historique cohérent, messages clairs

3. Choix Architecturaux (/10 points)

Pour les groupes Backend :

  • Justification des choix techniques (3 pts) : Stack, architecture, trade-offs
  • Respect des principes REST (3 pts) : Nommage URLs, verbes HTTP, statelessness, codes HTTP
  • Sécurité (2 pts) : API Keys sécurisées, validation, HTTPS, CORS
  • Fonctionnalités avancées (2 pts) : Versioning, pagination, filtrage, rate limiting (bonus)

Pour le groupe Frontend :

  • Justification des choix techniques (3 pts) : Stack, approche authentification, trade-offs
  • Architecture d'authentification (4 pts) : JWT/OAuth corrects, choix utilisateur, sécurité tokens
  • Intégration des backends (2 pts) : Stratégie 4 APIs, API Keys sécurisées, gestion timeouts
  • Gestion des erreurs (1 pt) : Stratégie fallback, retry (bonus), feedback utilisateur

4. Présentation Orale et Démo Live (/10 points)

Durée : 20-30 minutes par groupe

Structure imposée :

  • Présentation du thème et contexte (2-3 min) - /2 pts : Problématique, valeur ajoutée, public cible
  • Architecture et choix techniques (5-7 min) - /3 pts : Schéma architecture, stack, BDD, sécurité, patterns
  • Démonstration live (8-10 min) - /3 pts : Endpoints principaux, Postman, API Keys, erreurs (Backend) / Authentification, consommation APIs, erreurs réseau (Frontend)
  • Difficultés rencontrées et solutions (3-5 min) - /1 pt : Problèmes, solutions, apprentissages
  • Améliorations futures (2-3 min) - /1 pt : Ce qui manque, prochaines étapes, scalabilité
  • Questions/Réponses (5-10 min) : Évaluation transversale

🎁 Points Bonus (Maximum +5 points)

Les points bonus s'ajoutent à la note finale (plafonnée à 40/40).

Pour tous les groupes :

  • CI/CD implémenté (+2 pts) : GitHub Actions, GitLab CI, tests automatisés, déploiement automatique
  • Docker / Docker Compose (+1 pt) : Dockerfile fonctionnel, docker-compose.yml, instructions claires
  • Tests automatisés (+1 pt) : Tests unitaires, tests d'intégration, coverage > 50%
  • Rate Limiting (+0.5 pt) : Implémentation, configuration documentée
  • Monitoring / Logs (+0.5 pt) : Logs structurés, système de monitoring

Pour les groupes Backend uniquement :

  • HATEOAS (+1 pt) : Liens hypermedia, navigation découvrable

Pour le groupe Frontend uniquement :

  • PWA (Progressive Web App) (+1 pt) : Service Worker, fonctionne offline, installable
  • Internationalisation (i18n) (+0.5 pt) : Support plusieurs langues, FR + EN minimum

💡 Conseils et bonnes pratiques

Pour les groupes Backend

1. Commencez par le contrat API

  • Définissez vos endpoints avant de coder
  • Utilisez Swagger Editor en ligne
  • Faites valider par le groupe Frontend

2. Adoptez une architecture claire

src/
├── routes/       # Définition des endpoints
├── controllers/  # Logique de traitement
├── services/     # Logique métier
├── models/       # Modèles de données
├── middlewares/  # Auth, validation, etc.
└── utils/        # Fonctions utilitaires

3. Sécurisez vos API Keys

  • Ne jamais commit les clés en dur
  • Utilisez des variables d'environnement
  • Hashez les clés en base de données
  • Permettez la régénération

4. Gérez les erreurs proprement

try {
  // logique
} catch (error) {
  return res.status(500).json({
    error: 'Internal Server Error',
    message: error.message,
    timestamp: new Date().toISOString()
  });
}

5. Codes HTTP corrects

  • 200 : OK
  • 201 : Created
  • 400 : Bad Request
  • 401 : Unauthorized
  • 403 : Forbidden
  • 404 : Not Found
  • 500 : Internal Server Error

6. Testez avec Postman

  • Créez une collection complète
  • Utilisez des variables d'environnement
  • Testez tous les cas d'erreur

Pour le groupe Frontend

1. Architecture de l'authentification

src/
├── auth/
│   ├── JWTAuth.js      # Gestion JWT
│   ├── OAuth2Auth.js   # Gestion OAuth 2.0
│   └── AuthContext.js  # Context global
├── services/
│   ├── api1Service.js  # Appels API Backend 1
│   ├── api2Service.js  # Appels API Backend 2
│   ├── api3Service.js  # Appels API Backend 3
│   └── api4Service.js  # Appels API Backend 4
└── utils/
    └── apiKeyManager.js # Gestion des API Keys

2. Sécurisez le stockage des tokens

  • Utilisez httpOnly cookies pour JWT (meilleur que localStorage)
  • Ou localStorage avec précautions (XSS)
  • Implémentez le refresh token

3. Gérez les erreurs réseau

try {
  const response = await fetch(API_URL, {
    headers: { 'X-API-Key': API_KEY }
  });
  
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  
  return await response.json();
} catch (error) {
  // Afficher un message utilisateur
  // Logger l'erreur
  // Retry si pertinent
}

4. Communiquez avec les groupes Backend

  • Demandez leurs contrats API tôt
  • Testez les endpoints avec Postman d'abord
  • Signalez les bugs rapidement
  • Proposez des améliorations

5. Utilisez des données mock

  • Pour développer sans dépendre des backends
  • Pour les démos si un backend est down
  • json-server, MSW, ou fichiers JSON statiques

Pour tous les groupes

Git : Bonnes pratiques

  • Commits fréquents avec messages clairs
  • Branches feature pour les nouvelles fonctionnalités
  • Pull Requests pour la revue de code
  • .gitignore complet (node_modules, .env, etc.)

Documentation continue
