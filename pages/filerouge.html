Backend du Frontend (BFF) — requis

Le frontend doit s’appuyer sur un petit backend dédié pour la sécurité et l’orchestration.

  • Proxy des appels vers les 4 APIs (le navigateur n’envoie jamais les API Keys directement).
  • Stockage et injection des API Keys côté serveur (secrets hors du navigateur).
  • Gestion de l’auth utilisateurs (JWT/OAuth 2.0), sessions si nécessaire.
  • Centralisation: CORS, rate limiting, logs, gestion des erreurs.
  • Agrégation d’appels (un endpoint pour plusieurs services côté front).

Bénéfices: sécurité, contrôle, simplification du client et meilleure observabilité.

🎯 OBJECTIFS PÉDAGOGIQUES
Ce projet fil rouge a pour objectif de vous faire mettre en pratique les principaux concepts vus en cours sur les Web Services, dans un contexte professionnel réaliste.
Vous devrez démontrer votre maîtrise de :

Conception et développement d'APIs REST
Sécurité des Web Services (authentification, autorisation, API Keys)
Documentation technique (OpenAPI/Swagger)
Choix architecturaux justifiés
Bonnes pratiques professionnelles


📋 DESCRIPTION DU PROJET
Contexte
Dans le cadre d'un écosystème SmartCity, plusieurs services indépendants doivent coexister et être accessibles via une application frontend centralisée.
La formation est divisée en 5 groupes :
🔧 4 Groupes Backend (4 personnes/groupe)
Chaque groupe développe un Web Service REST sur un thème SmartCity :

Groupe 1 : Service de diététique et nutrition
Groupe 2 : Service de diététique et nutrition (approche différente)
Groupe 3 : Service de gestion de parking et stationnement
Groupe 4 : Service d'alertes citoyennes

🎨 1 Groupe Frontend (3 personnes)
Développe une application frontend qui consomme les 4 APIs backend et gère l'authentification des utilisateurs finaux.

🔐 ARCHITECTURE DE SÉCURITÉ
Pour les groupes Backend
Authentification B2B (Backend ↔ Frontend) :

Utilisation d'API Keys pour authentifier le frontend (client de l'API)
Chaque groupe backend génère et fournit une API Key au groupe frontend
Les requêtes du frontend vers les backends doivent inclure cette API Key

Pourquoi des API Keys ?
C'est la pratique standard professionnelle pour les intégrations entre services (ex: Stripe, SendGrid, Google Maps API, etc.). Lorsqu'une application souscrit à une API tierce, elle reçoit une clé unique qui l'identifie.
Pour le groupe Frontend
Double authentification à implémenter :

Authentification des utilisateurs finaux (B2C) :

Implémentation de JWT (JSON Web Tokens)
Implémentation d'OAuth 2.0 (Google, GitHub, etc.)
L'utilisateur doit pouvoir choisir sa méthode d'authentification


Authentification vers les backends (B2B) :

Utilisation des API Keys fournies par chaque groupe backend
Envoi de l'API Key dans les headers des requêtes vers les backends



Schéma d'authentification Frontend :
Utilisateur Final
    │
    ├─ Option 1 : Login/Password → JWT généré par le Frontend
    └─ Option 2 : OAuth 2.0 (Google, GitHub...) → Token OAuth
    
    ↓ (utilisateur authentifié)
    
Frontend (possède le JWT ou OAuth Token)
    │
    └─ Appels vers les 4 backends avec API Key dans les headers
        
        Backend 1 → Vérifie API Key → Répond
        Backend 2 → Vérifie API Key → Répond
        Backend 3 → Vérifie API Key → Répond
        Backend 4 → Vérifie API Key → Répond

💡 CONSEILS ET BONNES PRATIQUES
Pour les groupes Backend

Commencez par le contrat API

Définissez vos endpoints avant de coder
Utilisez Swagger Editor en ligne
Faites valider par le groupe Frontend


Adoptez une architecture claire

   src/
   ├── routes/       # Définition des endpoints
   ├── controllers/  # Logique de traitement
   ├── services/     # Logique métier
   ├── models/       # Modèles de données
   ├── middlewares/  # Auth, validation, etc.
   └── utils/        # Fonctions utilitaires

Sécurisez vos API Keys

Ne jamais commit les clés en dur
Utilisez des variables d'environnement
Hashez les clés en base de données
Permettez la régénération


Gérez les erreurs proprement

javascript   try {
     // logique
   } catch (error) {
     return res.status(500).json({
       error: 'Internal Server Error',
       message: error.message,
       timestamp: new Date().toISOString()
     });
   }
```

5. **Codes HTTP corrects**
   - 200 : OK
   - 201 : Created
   - 400 : Bad Request
   - 401 : Unauthorized
   - 403 : Forbidden
   - 404 : Not Found
   - 500 : Internal Server Error

6. **Testez avec Postman**
   - Créez une collection complète
   - Utilisez des variables d'environnement
   - Testez tous les cas d'erreur

### Pour le groupe Frontend

1. **Architecture de l'authentification**
```
   src/
   ├── auth/
   │   ├── JWTAuth.js      # Gestion JWT
   │   ├── OAuth2Auth.js   # Gestion OAuth 2.0
   │   └── AuthContext.js  # Context global
   ├── services/
   │   ├── api1Service.js  # Appels API Backend 1
   │   ├── api2Service.js  # Appels API Backend 2
   │   ├── api3Service.js  # Appels API Backend 3
   │   └── api4Service.js  # Appels API Backend 4
   └── utils/
       └── apiKeyManager.js # Gestion des API Keys

Sécurisez le stockage des tokens

Utilisez httpOnly cookies pour JWT (meilleur que localStorage)
Ou localStorage avec précautions (XSS)
Implémentez le refresh token


Gérez les erreurs réseau

javascript   try {
     const response = await fetch(API_URL, {
       headers: { 'X-API-Key': API_KEY }
     });
     
     if (!response.ok) {
       throw new Error(`HTTP ${response.status}`);
     }
     
     return await response.json();
   } catch (error) {
     // Afficher un message utilisateur
     // Logger l'erreur
     // Retry si pertinent
   }
