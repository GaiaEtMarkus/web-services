📋 Quiz de Révision - Jour 7

Ce quiz contient 20 questions de révision sur les Microservices et l'Architecture Distribuée. Cliquez sur une question pour afficher la réponse détaillée.

🧱 Questions sur l'Architecture Microservices

Question 1: Qu'est-ce qu'un microservice et quelles sont ses 5 caractéristiques principales ?

Réponse attendue

Un microservice est un service petit, autonome et fortement encapsulé.

Les 5 caractéristiques principales :

  1. Single Responsibility : Un service = un domaine métier (Events, Users, Payments...)
  2. Base de données privée : Chaque service possède sa propre base de données
  3. API explicite : Communication via REST, gRPC ou messages
  4. Déploiement indépendant : Chaque service peut être déployé séparément
  5. Équipe autonome : "Two Pizza Team" - une équipe suffisamment petite pour être nourrie avec deux pizzas
Question 2: Comparez Monolithe, SOA et Microservices en 5 critères clés.

Réponse attendue

5 critères de comparaison :

  1. Complexité initiale :
    • Monolithe : ✅ Simple
    • SOA : ⚠️ Élevée (ESB, gouvernance)
    • Microservices : ❌ Complexe (infra, CI/CD)
  2. Scalabilité :
    • Monolithe : Verticale (+CPU/RAM)
    • SOA : Horizontale mais via ESB
    • Microservices : Horizontale par service
  3. Base de données :
    • Monolithe : Unique
    • SOA : Souvent partagée / modèle canonique
    • Microservices : Une par service
  4. Résilience :
    • Monolithe : ❌ Point unique de défaillance
    • SOA : ⚠️ ESB = SPOF si mal dimensionné
    • Microservices : ✅ Isolation des pannes
  5. Technologies :
    • Monolithe : Stack unique
    • SOA : Standards WS-*, SOAP
    • Microservices : Liberté par service
Question 3: Quand utiliser ou éviter les microservices ? Donnez 3 arguments pour chaque cas.

Réponse attendue

✅ Adoptez les microservices si :

  • Équipe > 15 personnes avec besoin d'autonomie
  • Domaines métier multiples (Events, Users, Billing...)
  • Charges différentes nécessitant du scaling fin (Events 1000 req/s vs Users 10 req/s)

❌ Restez monolithe si :

  • Startup/MVP : vitesse > architecture
  • Petite équipe (<10) ou budget limité
  • Pas d'expertise DevOps (Kubernetes, observabilité)

Citation de Martin Fowler : "Don't start with microservices. Start with a monolith and split when the pain is real."

Signaux de migration : Déploiement > 30 min, équipes qui se marchent dessus, scalabilité fine impossible, base de données saturée.

Question 4: Citez les 4 défis majeurs des microservices et leurs solutions.

Réponse attendue

Les 4 défis majeurs :

  1. Complexité opérationnelle (50 services = 50 repos, déploiements, pipelines)
    • Solutions : Kubernetes, Docker, CI/CD (GitHub Actions), Infra as Code (Terraform)
  2. Communication inter-services (latence réseau cumulée)
    • Solutions : Caching (Redis), Messaging asynchrone (RabbitMQ, Kafka), API Gateway
  3. Données distribuées (pas de transactions ACID multi-services)
    • Solutions : Saga Pattern, Eventual Consistency, Event Sourcing
  4. Monitoring & debugging (une requête traverse 5 services)
    • Solutions : Distributed Tracing (Jaeger, Zipkin), Centralized Logging (ELK), Correlation ID
Question 5: Qu'est-ce qu'un Correlation ID et pourquoi est-il essentiel ?

Réponse attendue

Un Correlation ID est un identifiant unique généré au début d'une requête et propagé à travers tous les services appelés.

Pourquoi c'est essentiel :

  • Permet de tracer une requête qui traverse plusieurs services
  • Facilite le debugging en filtrant les logs par cet ID
  • Indispensable pour le distributed tracing

Exemple de flux :

// API Gateway génère l'ID
const correlationId = uuidv4();
req.headers['x-correlation-id'] = correlationId;

// Dans les logs :
[abc-123] Gateway: Received request
[abc-123] Events Service: Fetching event
[abc-123] Payment Service: Processing payment
[abc-123] Notification Service: Sending email

🚪 Questions sur l'API Gateway

Question 6: Qu'est-ce qu'une API Gateway et quelle est la différence avec un simple reverse proxy ?

Réponse attendue

Une API Gateway est le point d'entrée officiel de tous les clients (web, mobile, partenaires) vers le système.

Différence avec un reverse proxy :

  • Reverse proxy : Simple redirection de requêtes basée sur l'URL
  • API Gateway : Comprend les notions métier ("/api/events" → Events Service) et applique des politiques uniformes

Analogie : La réception d'un hôtel - on passe toujours par elle avant d'accéder aux chambres.

Avantages :

  • Une seule URL publique
  • Authentification centralisée
  • Masque la topologie interne
  • Point stratégique pour observabilité, A/B testing, cache
Question 7: Citez les 6 responsabilités clés d'une API Gateway.

Réponse attendue

Les 6 responsabilités clés :

  1. Routage : Rediriger chaque endpoint vers le service cible 
    /api/events → http://events:3001
/api/users → http://users:3002
  2. Authentification : Vérifier le JWT une seule fois puis propager l'identité (x-user-id, x-user-role)
  3. Rate limiting : Limiter les abus (DDOS, bots) - ex: max 100 requêtes / 15 min
  4. Load balancing : Répartir la charge sur plusieurs instances (round-robin)
  5. Agrégation : Composer un dashboard en un seul appel (Promise.all sur plusieurs services)
  6. Cache & transformation : Mettre en cache les réponses (Redis), transformer les formats
Question 8: L'API Gateway est-elle un point de défaillance unique (SPOF) ? Comment le mitiger ?

Réponse attendue

Oui, l'API Gateway est potentiellement un SPOF car toutes les requêtes passent par elle. Si elle tombe, tout le système devient inaccessible.

Stratégies de mitigation :

  1. Haute disponibilité (HA) : Déployer plusieurs instances de la Gateway derrière un load balancer
  2. Health checks : Surveiller la Gateway et basculer automatiquement sur une instance saine
  3. Stateless : La Gateway ne doit stocker aucun état (permet le scaling horizontal)
  4. Timeouts et Circuit Breaker : Éviter que la Gateway soit bloquée par un service lent
  5. Caching : Réduire la charge sur les services backend

Architecture résiliente :

Load Balancer (HAProxy, AWS ALB)
       │
   ┌───┴───┐
   │       │
Gateway1  Gateway2  (plusieurs instances)
   │       │
   └───┬───┘
       │
   Services

Principe clé : La Gateway doit rester "légère" - elle route, authentifie et limite, mais ne contient pas de logique métier complexe.

🔍 Questions sur le Service Discovery

Question 9: Pourquoi le Service Discovery est-il nécessaire dans une architecture microservices ?

Réponse attendue

Problème : Avec des services qui scalent automatiquement (nouvelles instances, IPs dynamiques), comment savoir où envoyer les requêtes ? Impossible de maintenir un fichier de configuration manuel si les IPs changent toutes les minutes.

Service Discovery = un annuaire dynamique, le "DNS intelligent" des microservices.

Sans Service Discovery (❌) :

  • Configuration statique des IPs
  • Maintenance manuelle (erreurs, oublis)
  • Impossible de supporter le scaling horizontal
  • Downtime dès qu'une IP change

Avec Service Discovery (✅) :

  • Enregistrement et retrait automatiques
  • Health-checks pour ne router que vers les instances saines
  • Support du scaling et des déploiements rolling
Question 10: Décrivez le cycle d'enregistrement/découverte d'un service.

Réponse attendue

Cycle en 4 étapes :

  1. Enregistrement : Le service démarre → s'enregistre dans le registre avec son nom ("events"), IP, port et tags
  2. Health-checks : Le registre exécute des health-checks périodiques (/health) pour vérifier la disponibilité
  3. Résolution : Les clients (gateway, autres services) interrogent le registre pour obtenir les instances valides
  4. Retrait : En cas de panne, le registre retire l'instance et renvoie uniquement les nœuds healthy
1. Service Events démarre → s'enregistre ("events", 10.0.1.5:3001)
2. Le registre vérifie périodiquement /health
3. La Gateway demande : "Donne-moi une instance de events"
4. Le registre renvoie la liste healthy
5. La Gateway choisit une instance (round-robin) et route l'appel
6. Si l'instance ne répond plus, elle est retirée automatiquement
Question 11: Comparez Consul et Kubernetes pour le Service Discovery.

Réponse attendue

Consul (HashiCorp) :

  • Registre distribué + DNS + KV store
  • S'installe comme un cluster de serveurs
  • Chaque service s'enregistre via un agent local ou une API HTTP
  • Expose l'inventaire via HTTP, DNS ou client officiel
  • Permet des health-checks très fins et des métadonnées (tags, version, datacenter)

Kubernetes (natif) :

  • Chaque "Service" K8s possède un DNS interne (http://events-service)
  • Le DNS est mis à jour automatiquement quand les pods scalent ou se redéploient
  • Les probes (liveness/readiness) déterminent si un pod est routable
  • Pas besoin d'outil externe pour un déploiement Cloud-native

Différence clé : Consul est un outil dédié (multi-environnement), Kubernetes intègre le Service Discovery nativement.

Question 12: Pourquoi les health checks sont-ils essentiels et que doivent-ils vérifier ?

Réponse attendue

Pourquoi les health checks sont essentiels :

  • Permettent au Service Discovery de savoir quelles instances sont disponibles
  • Évitent de router du trafic vers des services défaillants
  • Permettent le retrait automatique des instances en panne
  • Facilitent les déploiements rolling (attendre qu'une instance soit prête avant de router)

Que doit vérifier un bon health check ?

  1. Connexion à la base de données : Le service peut-il exécuter une requête simple ?
  2. Dépendances critiques : Redis, message broker, APIs externes essentielles
  3. Ressources : Mémoire, CPU, espace disque suffisants ?

Ce qu'il ne faut PAS faire :

  • ❌ Vérifier des dépendances non-critiques (un service de statistiques down ne doit pas rendre le service "unhealthy")
  • ❌ Health check trop lent ou coûteux (appelé toutes les 10 secondes !)
  • ❌ Retourner "healthy" sans vraiment vérifier les dépendances

Principe : Un health check doit répondre vite (<100ms) et vérifier uniquement ce qui empêcherait le service de fonctionner.

⚡ Questions sur les Patterns Essentiels

Question 13: Expliquez le Circuit Breaker et ses 3 états.

Réponse attendue

Circuit Breaker = disjoncteur logiciel qui coupe les appels après N échecs pour éviter l'effet domino (cascade de défaillances).

Problème résolu : Si Service B est down et que Service A continue de l'appeler (timeout 5s), 100 req/s × 5s = 500 threads bloqués → A finit par tomber aussi.

Les 3 états :

  1. CLOSED : Fonctionnement normal, les requêtes passent
    • Si N échecs consécutifs → passe à OPEN
  2. OPEN : Toutes les requêtes échouent instantanément (fail fast)
    • Après un délai (ex: 60s) → passe à HALF-OPEN
  3. HALF-OPEN : On teste 1 requête
    • Succès → retour à CLOSED
    • Échec → retour à OPEN

Libraries : Node.js – opossum, Java – Resilience4j, Python – pybreaker

Question 14: Qu'est-ce que le Saga Pattern et pourquoi est-il nécessaire ?

Réponse attendue

Problème : Dans les microservices, chaque service a sa propre base de données. Il est donc impossible d'avoir une transaction ACID globale couvrant Order + Payment + Reservation.

Saga Pattern = orchestration de transactions locales avec des opérations de compensation en cas d'échec.

Exemple : Créer une commande = Order + Payment + Reservation + Notification

  • Chaque service effectue sa transaction locale
  • Si une étape échoue, on déclenche les compensations (annulation, remboursement)

Rappel ACID : Atomicité, Cohérence, Isolation, Durabilité - garanties assurées par un moteur de base de données unique, impossibles nativement en distribué.

Question 15: Comparez Chorégraphie et Orchestration pour les Sagas.

Réponse attendue

Chorégraphie (event-driven) :

Order Service → publie "OrderCreated"
Payment Service → écoute, tente le débit
  ↳ succès : publie "PaymentProcessed"
  ↳ échec : publie "PaymentFailed"
Event Service → écoute "PaymentProcessed"
  ↳ succès : publie "SeatReserved"
  ↳ échec : publie "ReservationFailed" (→ refund)
  • ✅ Décentralisé, scalable, pas de SPOF
  • ❌ Difficile à tracer/debugger

Orchestration :

  • Un orchestrateur central contrôle tout le flux
  • ✅ Vue globale, debugging facile
  • ❌ Orchestrateur = point central de défaillance

Tableau comparatif :

  • Complexité : Chorégraphie ⚠️ élevée | Orchestration ✅ plus simple
  • Couplage : Chorégraphie ✅ faible | Orchestration ⚠️ moyen
  • Point de défaillance : Chorégraphie ✅ aucun | Orchestration ❌ orchestrateur
  • Debugging : Chorégraphie ❌ difficile | Orchestration ✅ facile
Question 16: Quelle est la différence entre communication synchrone et asynchrone (Event-Driven) ?

Réponse attendue

Synchrone (❌) :

Client → Gateway → Order Service (attend 2s)
                 → Payment Service (attend 1s)
                 → Notification Service (attend 3s)
= 6s de latence, tout échoue si Notification down

Asynchrone / Event-Driven (✅) :

Client → Gateway → Order Service (réponse 200ms)
Order Service publie "OrderCreated" dans RabbitMQ
Payment / Notification / Analytics consomment en parallèle

Avantages de l'Event-Driven :

  • Découplage total entre services
  • Résilience : si un consumer est down, les autres continuent
  • Scalabilité horizontale des consumers
  • Performance : réponse rapide au client
Question 17: Qu'est-ce que le pattern "Database per Service" et quels problèmes pose-t-il ?

Réponse attendue

Database per Service = chaque microservice possède sa propre base de données, inaccessible directement par les autres services.

Pourquoi ce pattern ?

  • Autonomie : Chaque équipe peut choisir sa technologie de stockage (PostgreSQL, MongoDB, Redis...)
  • Découplage : Un changement de schéma n'impacte pas les autres services
  • Scalabilité : Chaque base peut être optimisée et scalée indépendamment
  • Isolation des pannes : Si une base tombe, seul son service est impacté

Problèmes posés :

  1. Pas de transactions ACID cross-services : Impossible de faire un rollback global → nécessite le Saga Pattern
  2. Jointures impossibles : Pour afficher "commande + utilisateur", il faut appeler 2 services
  3. Duplication de données : Parfois nécessaire de copier des données entre services (ex: nom utilisateur dans le service Commande)
  4. Cohérence à terme (Eventual Consistency) : Les données ne sont pas synchronisées instantanément

Règle d'or : Un service ne doit JAMAIS accéder directement à la base d'un autre service. Toujours passer par l'API.

Question 18: Expliquez les patterns Timeout, Retry + Backoff, et Bulkhead.

Réponse attendue

1. Timeout :

  • Ne jamais attendre indéfiniment une réponse
  • Définir une limite de temps (ex: 5 secondes)
  • Si dépassé → abort et erreur

2. Retry + Backoff Exponentiel :

  • Réessayer automatiquement en cas d'échec
  • Backoff exponentiel : attendre de plus en plus longtemps (2s, 4s, 8s...)
  • Évite de surcharger un service en difficulté
Tentative 1 : échec → attendre 2s
Tentative 2 : échec → attendre 4s
Tentative 3 : échec → attendre 8s
Tentative 4 : abandon

3. Bulkhead (cloisons) :

  • Isoler les ressources pour éviter qu'un service saturé consomme toutes les connexions
  • Exemple : max 10 requêtes simultanées vers Payment Service
  • Si limite atteinte → les autres requêtes attendent ou échouent
  • Protège les autres services de l'effet domino

🎯 Questions de Synthèse

Question 19: Qu'est-ce que l'Eventual Consistency et pourquoi l'accepter en microservices ?

Réponse attendue

Eventual Consistency (cohérence à terme) = les services ne sont pas synchronisés instantanément, mais ils convergent vers un état cohérent.

Exemple :

  • Service Commande traite une commande
  • Service Stock reçoit l'événement 50 ms après
  • Service Notification reçoit l'événement 200 ms plus tard
  • Pendant ce délai, les services sont dans des états "incohérents" mais ils finissent par converger

Pourquoi l'accepter ?

  • ✅ Permet des échanges asynchrones (Kafka, RabbitMQ)
  • ✅ Meilleure scalabilité horizontale
  • ✅ Pas de transactions distribuées complexes
  • ✅ Résilience : un service down ne bloque pas les autres

Trade-off : On échange la cohérence immédiate contre la performance et la résilience.

Question 20: Décrivez le flux complet d'une requête "Créer un événement" dans SmartCity.

Réponse attendue

Flux typique en 6 étapes :

  1. Client envoie POST /api/events → API Gateway
  2. Gateway vérifie le JWT (authentification centralisée)
  3. Gateway route vers Events Service (:3001) via Service Discovery
  4. Events Service crée l'événement dans sa base (Postgres Events)
  5. Events Service publie EventCreated dans RabbitMQ
  6. Notification Service consomme l'événement et envoie un email de confirmation

Patterns utilisés :

  • API Gateway : point d'entrée unique, auth, routage
  • Service Discovery : localisation dynamique des services
  • Event-Driven : communication asynchrone via RabbitMQ
  • Database per Service : chaque service a sa propre base
